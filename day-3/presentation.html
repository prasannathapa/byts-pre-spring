first, the point of all of it

One API. Any database. Your code never knows which.

JDBC is a set of interfaces in java.sql. The driver jar is the implementation. The database gets chosen at runtime, by a string.

  • This API is from 1997. It is boring, and it is on every machine you will ever deploy to.
  • Every data framework you meet sits on exactly this, including the one somebody teaches you next week.
  • Know the floor before you stand on the carpet.

architecture / the driver's job

Four kinds of driver. Only one of them still matters.

A driver is a jar that implements java.sql.Driver and friends, and turns your interface calls into that vendor's wire protocol.

TypeWhat it isWhere it lives now
1JDBC-ODBC bridge, native ODBC underneathremoved from the JDK in Java 8. Dead.
2thin Java over a vendor C libraryyou must install the client. Oracle OCI is the survivor.
3talks to a middleware server, which talks to the databasehistorical.
4pure Java, speaks the database's own protocol over a socketone jar, no install: h2, postgresql, mysql-connector-j, ojdbc11.
  • A driver implements Driver, Connection, Statement, PreparedStatement, CallableStatement and ResultSet. That is all it is.
  • It is a runtime dependency. Your code never imports it.
  • A driver that does not recognise your URL returns null and says nothing, which is how several of them live on one classpath.

driver loading / guess first

How does DriverManager find a driver it has never heard of?

You never wrote new org.h2.Driver() and you never named H2 in code at all. Does something scan the classpath, does the URL carry the class name, or does the jar say who it is?

  • The jar says who it is. Since JDBC 4.0 every driver ships one text file, META-INF/services/java.sql.Driver, holding its Driver class name.
  • Your first getConnection runs ServiceLoader.load(Driver.class) once, instantiates each class named in those files, and each one registers itself from its own static initialiser. It is lazy, and I checked this on JDK 25: the lookup happens on first use.
  • Then getConnection(url) walks the registered drivers in order and calls connect(url, props). Not yours? Return null. First non-null wins. All null and you get No suitable driver found.
driver loadingserviceloader
the fine print

Class.forName, and the global that outlives your app.

  • Class.forName("org.h2.Driver") is the pre-2006 trick: it initialised the class, whose static block called DriverManager.registerDriver.
  • Today it is redundant, and since registration is lazy it makes registration happen earlier, not later.
  • A class initialiser runs at most once, so it cannot register twice. getDrivers() still shows one H2 driver.
  • You will see that line in every tutorial older than you are. It is a tell, not a bug.
  • What it is really telling you: DriverManager is a static, JVM-wide global, with all the trouble Day 1 said globals cause.
  • Tomorrow's version of that trouble: a driver jar inside a WAR registers itself with the JVM-wide DriverManager and never deregisters, so Tomcat logs "the web application registered the JDBC driver but failed to unregister it" and leaks a classloader on every redeploy.
  • Which is one more reason production code asks a DataSource for its connections. That is part 2.

Anatomy of a JDBC URL.

jdbc : subprotocol : subname. The subprotocol is what each driver's connect(url) matches on, and everything after it belongs to that vendor.

URLWhat the pieces mean
jdbc:h2:mem:bank;DB_CLOSE_DELAY=-1in memory, this JVM only, and it survives the last close
jdbc:h2:./data/bankthe same H2, writing files on disk
jdbc:postgresql://db.example:5432/bankhost, port, database name
jdbc:mysql://db.example:3306/bank?serverTimezone=UTCoptions ride in a query string

connection / guess first

What does one getConnection() actually cost?

It is one line of Java. Nanoseconds, like new ArrayList()? Microseconds? Or milliseconds, plural?

  • Milliseconds, plural, and here is where they go: DNS lookup, TCP handshake, TLS handshake, authentication round trips, session setup on the server.
  • 5 to 50 milliseconds and several round trips to make one. Four orders of magnitude more than allocating an object.
  • It holds an open socket plus a server-side session that costs the database memory, and in PostgreSQL a whole backend process.
  • It is not thread-safe. One thread at a time, ever.

the standard recipe

The six steps, and which ones you still write.

StepWhat the textbook saysWhat you actually write in 2026
1load and register the driver, Class.forNamenothing. ServiceLoader did it.
2establish a connection, DriverManager.getConnectionyes, or ds.getConnection() from a pool in production
3create a statement, createStatementprepareStatement, almost always
4execute the SQLyes, after binding every parameter
5process the ResultSet, while (rs.next())yes, through one mapper per table

Steps 1 and 6 were half the old boilerplate, and both are now the language's job or the platform's. That is what twenty years of a stable API looks like.

statementquestion
the answer

Every row. Your data just became code.

The string the parser actually receives: SELECT * FROM account WHERE owner = 'x' OR '1'='1'

  • The parser cannot see where your SQL ended and the user's text began, because there is no boundary. It is one string.
  • Escaping apostrophes is an arms race, and you lose it to encodings, comments and vendor syntax.
  • The fix is structural: send the code and the data as two separate things, so the parser has finished before the value arrives.

the move

PreparedStatement: the SQL is fixed before the data arrives.

concatenated 

String sql = "SELECT * FROM account"
    + " WHERE owner = '" + name + "'";
Statement s = c.createStatement();
ResultSet rs = s.executeQuery(sql);
bound 

try (PreparedStatement ps = c.prepareStatement(
        "SELECT id, owner, balance_cents"
      + " FROM account WHERE owner = ?")) {
    ps.setString(1, name);
    try (ResultSet rs = ps.executeQuery()) { ... }
}
  • The ? is a hole in a statement that has already been parsed.
  • The value travels as a typed parameter and is never re-parsed, so x' OR '1'='1 is just an odd name that matches nobody.
  • Parameters are 1-based, because JDBC is older than you are and everything in it is 1-based.
  • The server can cache the plan and reuse it, so the safe way is also the fast way.

the fine print

What a ? can bind, and what it cannot.

  • A ? binds a value: a string, a number, a date, a null. That is the whole list.
  • It cannot bind a table name, a column name, an ORDER BY direction, or a whole list for IN (?). For those you whitelist and concatenate, or write one ? per element.
  • Null needs a type. setNull(i, Types.BIGINT) always works; setObject(i, null) works on H2 and PostgreSQL and fails on Oracle and Derby, because the driver cannot guess the column type.
  • LIKE: put your wildcard in the value, ps.setString(1, prefix + "%"). Never LIKE '?%'.
  • And escape theirs. Binding stops injection; it does not stop a user-typed % from being a wildcard. Use LIKE ? ESCAPE '!' with esc(s) = s.replace("!","!!").replace("%","!%").replace("_","!_"), or a search box for one customer will list all of them.
  • Prefer setObject(i, LocalDate), JDBC 4.2, over java.sql.Date. Day 1 told you why java.sql.Timestamp is a trap.
  • Set every parameter before you execute. Reusing a PreparedStatement in a loop is set, execute, repeat, and batching builds straight on that.

crud / the other three verbs

Insert, update, delete: the count is the answer.


try (PreparedStatement ps = c.prepareStatement(
        "INSERT INTO account(owner, balance_cents) VALUES (?, ?)")) {
    ps.setString(1, owner);
    ps.setLong(2, cents);
    int rows = ps.executeUpdate();          // 1
}

try (PreparedStatement ps = c.prepareStatement(
        "UPDATE account SET balance_cents = balance_cents + ? WHERE id = ?")) {
    ps.setLong(1, cents);
    ps.setLong(2, id);
    if (ps.executeUpdate() != 1) throw new NoSuchAccountException(id);
}
  • executeUpdate returns the number of rows the statement changed, and that number is the only way you learn an UPDATE matched nothing. A zero-row update is not an error, so compare the count to what you expected every time. That one habit will save you in the capstone.
  • A delete is the same shape, DELETE FROM account WHERE id = ?, and you check the count the same way. A DELETE or an UPDATE with no WHERE is valid SQL and will ruin an afternoon, so write the WHERE first.
  • The arithmetic in balance_cents = balance_cents + ? happens in the database. That matters enormously later today.

  • It throws. The cursor starts before the first row, so the idiom is while (rs.next()), or if (rs.next()) for a single row.

One Statement, one open cursor.

one statement, two queries 

try (Statement s = c.createStatement();
     ResultSet a = s.executeQuery("SELECT id FROM account")) {
    while (a.next()) {
        try (ResultSet t = s.executeQuery(
            "SELECT COUNT(*) FROM txn WHERE account_id = "
            + a.getLong(1))) { ... }
    }
}
// the inner executeQuery closes a, and the next a.next() throws
one statement each 

try (Statement s = c.createStatement();
     PreparedStatement inner = c.prepareStatement(
         "SELECT COUNT(*) FROM txn WHERE account_id = ?");
     ResultSet a = s.executeQuery("SELECT id FROM account")) {
    while (a.next()) {
        inner.setLong(1, a.getLong(1));
        try (ResultSet t = inner.executeQuery()) { ... }
    }
}
  • Every execution method on a Statement implicitly closes that Statement's current ResultSet. It is in the Javadoc, and it is the most common beginner crash in JDBC.
  • A parent closes its children, but a sibling replaces them. One Statement means one open cursor at a time.
  • And once you have fixed it this way, you have written a query per row. That is N+1, and there is a slide for it after lunch.

metadata / both of them

Two metadata interfaces: one for the database, one for the result set.

DatabaseMetaData md = c.getMetaData()

  • Who am I talking to: getDatabaseProductName(), getDatabaseProductVersion(), getDriverName(). On my machine: H2 2.3.232, JDBC 4.3. That is how your capstone test proves the driver really is H2.
  • What is in there: md.getTables(null, null, "ACCOUNT", new String[]{"TABLE"}), then getColumns, getPrimaryKeys, getImportedKeys. H2 and Oracle upper-case unquoted identifiers, so "account" is not an error, it is an empty result set, which is much worse.
  • What can you do here: supportsBatchUpdates(), supportsGetGeneratedKeys(), supportsTransactionIsolationLevel(level). Flyway, Liquibase and Hibernate all read this at startup.

ResultSetMetaData md = rs.getMetaData()

  • getColumnCount(), then getColumnLabel(i) for the alias you selected and getColumnName(i) for the underlying name. They differ the moment you write AS, and every getX(String) takes the label. Alias it, read the alias.
  • getColumnType(i) is the java.sql.Types int, getColumnTypeName(i) is the vendor's spelling, and getColumnClassName(i) tells you what getObject will hand back. That is how you discover your SUM came back as a BigDecimal.
  • You will rarely reach for it in application code, because you wrote the SELECT. It earns its keep where the code does not know its own query: a database browser, a CSV export, a generic Map mapper.

resultset / nulls and types

Reading typed values without lying.

The Java type int has no null, so something has to give. What it gives is a zero and a flag.


int b = rs.getInt("balance");                         // 0 when the column is NULL
if (rs.wasNull()) { /* and this is how you know which 0 it was */ }

Integer boxed = rs.getObject("balance", Integer.class);  // null. JDBC 4.1, honest.
LocalDate d   = rs.getObject("opened", LocalDate.class); // JDBC 4.2, skip java.sql.Date
long cents    = rs.getLong("balance_cents");             // or store cents, as we do
guessing the box 

long id = (Long) rs.getObject("id");
// ClassCastException when the column
// is INT: that is an Integer.
saying the type 

long id = rs.getObject("id", Long.class);
// or just rs.getLong("id"),
// which converts for you.
  • Primitive getters map SQL NULL to 0, false or 0.0 and raise a flag you must read with wasNull() straight after, before the next getter.
  • The untyped getObject returns whatever the type map says: INT gives Integer, BIGINT gives Long, NUMERIC gives BigDecimal, and a SUM changes the type under you on PostgreSQL. Pass the Class, or use a typed getter.

mapping / guess first

Where should "row to object" live?

Every query that touches account reads id, owner and balance_cents and builds an Account. Copy-pasted into every method? Inside an Account(ResultSet) constructor, so the domain object knows SQL? Or one small function per table, handed to a generic helper?

  • One function per table. And a function you can pass around is an instance of a one-method interface, which is all a lambda ever is.
  • Yesterday's four shapes: Function<T,R>, Predicate<T>, Consumer<T>, Supplier<T>. A method reference is the same thing written shorter: Demo::toAccount is an instance of whatever one-method interface the target type demands.
  • And here is the rule that decides today's design: a lambda may only throw the checked exceptions its interface's method declares.

Function<ResultSet, String> f = rs -> rs.getString("owner");
// error: unreported exception SQLException; must be caught or declared to be thrown

Function.apply declares nothing, so java.util.function is useless for anything that touches JDBC. That is why every JDBC library on earth declares its own row mapper interface. Effective Java, Item 71

mappingthe interface
the move

RowMapper: one function per table, a record per row.


record Account(long id, String owner, long balanceCents) { }
@FunctionalInterface
interface RowMapper<T> { T map(ResultSet rs) throws SQLException; }
static Account toAccount(ResultSet rs) throws SQLException {
    return new Account(rs.getLong("id"), rs.getString("owner"),
                       rs.getLong("balance_cents"));
}
static <T> List<T> query(Connection c, String sql, RowMapper<T> m, Object... args)
        throws SQLException {
    try (PreparedStatement ps = c.prepareStatement(sql)) {
        for (int i = 0; i < args.length; i++) ps.setObject(i + 1, args[i]);
        try (ResultSet rs = ps.executeQuery()) {
            List<T> out = new ArrayList<>();
            while (rs.next()) out.add(m.map(rs));
            return out;
        }
    }
}
  • Calling it: query(c, "SELECT ... WHERE balance_cents > ?", Demo::toAccount, 5000L). RowMapper<T> is Function<ResultSet,T> with the one thing Function lacks: a throws clause.
  • The mapper is the only place that knows column names, and it is injected into the query method, so the helper knows nothing about accounts. You have just written JdbcTemplate.query(sql, rowMapper, args) by hand.

transactionsquestion
the answer

Autocommit is on by default: every statement is its own transaction.

The money is gone.

  • With autocommit true, which is the JDBC default, each execute commits by itself the instant it finishes. The debit was durable before the credit was even parsed.
  • You draw the boundary yourself: setAutoCommit(false) to open, commit() to end, rollback() to undo everything since the start.
  • "Nobody called commit" is the wrong mental model, because nobody had to.

the move

The transfer, done right.


static void transfer(Connection c, long from, long to, long cents) throws SQLException {
    c.setAutoCommit(false);
    try (PreparedStatement debit = c.prepareStatement(
             "UPDATE account SET balance_cents = balance_cents - ? WHERE id = ?");
         PreparedStatement credit = c.prepareStatement(
             "UPDATE account SET balance_cents = balance_cents + ? WHERE id = ?")) {
        debit.setLong(1, cents);  debit.setLong(2, from);
        if (debit.executeUpdate() != 1) throw new NoSuchAccountException(from);
        credit.setLong(1, cents); credit.setLong(2, to);
        if (credit.executeUpdate() != 1) throw new NoSuchAccountException(to);
        c.commit();
    } catch (Exception e) {
        c.rollback();
        throw e;
    } finally {
        c.setAutoCommit(true);
    }
}
  • Catch Exception, not SQLException. That finally is a commit in disguise, so any unchecked exception escaping the catch leaves setAutoCommit(true) to make the half-done debit durable.
  • The table carries CHECK (balance_cents >= 0), so an overdraft makes the debit throw and the catch rolls back. A constraint is the last line of defence, not an if in Java, because two processes can both pass the same if.

the fine print

The shape every transaction method shares.

written once, body injected 

@FunctionalInterface
interface TxBody<T> { T run(Connection c) throws SQLException; }

static <T> T inTransaction(Connection c, TxBody<T> body) throws SQLException {
    c.setAutoCommit(false);
    try {
        T r = body.run(c);
        c.commit();
        return r;
    } catch (Throwable t) {
        try { c.rollback(); } catch (SQLException r) { t.addSuppressed(r); }
        throw t;
    } finally { c.setAutoCommit(true); }
}
  • Begin, work, commit, else roll back, always reset. Write it once and inject the body: Day 1's template method, with a lambda instead of a subclass. TxBody is Supplier-shaped, with the checked exception Supplier cannot express.
  • Catch Throwable: this helper is the one place that can guarantee the rollback. When rollback() itself fails, attach it as suppressed so the original failure is still the one in your log.
  • Warning: not re-entrant. A wrapped method calling another commits the outer one's half-finished work. In Spring that hole is called propagation.

  • A non-repeatable read means the same SELECT gives a different value the second time.
  • A phantom means the same SELECT returns a new row the second time.

isolationlevels
the answer, part 2

The lost update, frame by frame.

  • Read, compute in Java, write is not atomic even inside a transaction, because the database only serialised the two writes.
  • At READ_COMMITTED a plain SELECT takes no lock, so the second transaction happily held a value that was already stale.
  • This is not a database bug and not a Java bug. It is your SELECT making a promise it was never able to keep.
isolationlost update
the fixes

Three ways to stop losing it, and which one to reach for.


// 1. atomic: the read and the write are one statement
UPDATE account SET balance_cents = balance_cents + ? WHERE id = 1;

// 2. pessimistic: the second read blocks until the first transaction commits
SELECT balance_cents FROM account WHERE id = 1 FOR UPDATE;

// 3. optimistic: write only if nobody moved, then retry when 0 rows matched
UPDATE account SET balance_cents = ?, version = version + 1
 WHERE id = 1 AND version = ?;

atomic SQL

balance = balance + ?. The best fix whenever the new value is a function of the old one, because there is no read to go stale. Counters, balances, stock levels.

SELECT ... FOR UPDATE

For when you must read, decide in Java, then write. It holds the row lock for the rest of the transaction, so keep that short, and lock rows in a consistent order.

version column

Read the version, write WHERE version = ?, retry when 0 rows come back. No lock is held while a human thinks. This is exactly JPA's @Version.

  • Deadlock, concretely: transfer(1,2) at the same instant as transfer(2,1) leaves each side holding one row and waiting for the other. Touch the lower id first, whichever direction the money is going.
  • SERIALIZABLE is the fourth option, correct by construction, but now you catch 40001 and retry. The capstone uses fix 1 plus a CHECK constraint.

callable / guess first

The logic already lives in the database. How do you call it?

Your DBA hands you a procedure, transfer_funds(p_from, p_to, p_cents, OUT p_new_balance), and a function, fee_for(p_cents), that returns a number. Neither is a SELECT and neither is an INSERT.

  • There is a third statement type for exactly this. CallableStatement extends PreparedStatement, so everything you know about ? and binding still applies, and you create it with c.prepareCall(...).
  • Write the call in JDBC escape syntax, in curly braces: {call transfer_funds(?, ?, ?, ?)} for a procedure, {? = call fee_for(?)} for a function that returns a value.
  • The braces are the portable part. Oracle would otherwise want BEGIN transfer_funds(:1, :2); END; and SQL Server would want EXEC, and you write neither.
  • A procedure is called for its effect and returns values through OUT parameters. A function returns exactly one value and can also be used inside ordinary SQL, which is usually nicer, because then a plain PreparedStatement does the job.
  • Parameter directions: IN is an input and behaves like any ? you have bound today. OUT is an output, and you must declare its type in advance. INOUT is both, so you set it and declare it.
  • If a procedure returns result sets as well as OUT parameters, drain the result sets first and read the OUT parameters last: on several drivers the values are only there once everything else has been read.

pooling / the javax.sql.DataSource

500 requests a second. How many handshakes is that?

Each request opens a Connection, runs two queries and closes it. That is 500 handshakes a second at 20 ms each, plus the database creating and destroying 500 sessions a second.

  • One static shared Connection is the wrong fix: it is not thread-safe, it has one transaction state for everybody, and it is one socket for 500 requests.
  • A DataSource is an object with getConnection(), so you can inject it, configure it outside your code and swap it in a test. None of that is true of a static DriverManager.
  • A pooling DataSource keeps N real connections open and hands out thin wrappers. close() on the wrapper does not close the socket, it returns the connection, and getConnection() costs microseconds instead of a handshake.

optional / guess first

findById finds nothing. What do you return?

Your query helper returns a List, the caller wants exactly one account by id, and there is no row with that id. The signature promises an Account. Null? An exception? An empty list?

  • Returning null is the exact bug Optional was invented to prevent: the type says Account, the value says nothing, and the NullPointerException arrives three stack frames away. Optional<Account> says maybe in the signature, so the compiler makes the caller decide.
  • Chain without unwrapping: repo.findById(id).map(Account::balanceCents).orElse(0L). orElse gives a default, orElseGet takes a Supplier, and orElseThrow(() -> new NotFoundException(id)) is what a web layer usually wants.
  • The trap worth memorising: orElse evaluates its argument eagerly, every single time, even when the Optional is present. orElse(expensiveDefault()) runs the expensive call on the happy path too. orElseGet(() -> expensiveDefault()) does not. That is Item 55.
  • Never call get() without isPresent(), and preferably never call get() at all. Never make an Optional a field, a parameter or a collection element: it is a return type, and an Optional<List> is always a bug. Return an empty list.
  • When you meet Spring Data, findById returns Optional<T>, and now you know why. The capstone's repository returns it too.

And then there are ORMs, which are a bigger promise.

what to actually remember

Twelve lines, the whole day.

  • The driver is a Type 4 jar found by ServiceLoader, never named by you. H2 to MySQL is a URL and a jar.
  • A Connection is a socket, a session and a transaction, and it is not thread-safe.
  • SQL is code and values are data. A ? keeps them apart, and it can never bind an identifier.
  • A ResultSet is a cursor: next() first, wasNull or getObject(Class) for nulls, and read the label you selected.
  • One Statement has one open cursor, and a nested query kills its sibling.
  • Every handle is a resource: try-with-resources, reverse order, suppressed exceptions kept.
  • Autocommit is on until you say otherwise, and setAutoCommit(true) commits an open transaction, so catch wider than SQLException.
  • READ_COMMITTED permits the lost update. The fixes are atomic SQL, FOR UPDATE, or a version column.
  • Batch plus one transaction plus named generated keys is every import you will write.
  • CallableStatement with {call ...} and registerOutParameter is how you call the procedure somebody else wrote.
  • A DataSource is injected, and a pool makes close() a return, which is why you reset what you changed.
  • One repository per aggregate, SQL in one place, Optional for the missing row, exceptions translated at the door.

The database is shared,
remote and slow.
Treat it that way.

Shared, so isolation and constraints are not optional, and your Java if is not a lock. Remote, so every round trip and every open socket is a cost somebody else pays for. Slow, so batch, pool, push the filter down, and ask for exactly what you need. Everything a framework adds is a wrapper around those three facts.
