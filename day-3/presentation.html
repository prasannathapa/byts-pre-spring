Every row. Your data just became code.

the fine print

What a ? can bind, and what it cannot.

  • A ? binds a value: a string, a number, a date, a null. That is the whole list.
  • It can never bind an identifier. An identifier is the name of a thing in the statement, a table or a column, as against the values inside them. Names are part of the shape of the query, and the shape was fixed before your value turned up. ORDER BY ? and FROM ? are not a thing.
  • So for a column name you whitelist and concatenate, and for IN you write one ? per element. There is a question on this later, and most rooms get it wrong.
  • LIKE takes the wildcard in the value: ps.setString(1, prefix + "%"), never LIKE '?%'. And binding does not stop a user's own % from being a wildcard, so you escape theirs with LIKE ? ESCAPE '!', which the capstone makes you do.
  • Set every parameter before you execute. Set, execute, repeat is how you reuse one PreparedStatement in a loop, and batching builds straight on that.

crud / the other three verbs

Insert, update, delete: the count is the answer.


try (PreparedStatement ps = c.prepareStatement(
        "INSERT INTO account(owner, balance_cents) VALUES (?, ?)")) {
    ps.setString(1, owner);
    ps.setLong(2, cents);
    int rows = ps.executeUpdate();          // 1
}

try (PreparedStatement ps = c.prepareStatement(
        "UPDATE account SET balance_cents = balance_cents + ? WHERE id = ?")) {
    ps.setLong(1, cents);
    ps.setLong(2, id);
    if (ps.executeUpdate() != 1) throw new NoSuchAccountException(id);
}
  • executeUpdate returns the number of rows the statement changed, and that number is the only way you learn an UPDATE matched nothing. A zero-row update is not an error, so compare the count to what you expected every time. That one habit will save you in the capstone.
  • A delete is the same shape, DELETE FROM account WHERE id = ?, and you check the count the same way. A DELETE or an UPDATE with no WHERE is valid SQL and will ruin an afternoon, so write the WHERE first.
  • The arithmetic in balance_cents = balance_cents + ? happens in the database. That matters enormously later today.

resultsetthe cursor
not a list. A position.

The cursor, one frame at a time.

A ResultSet is not a collection of rows sitting in your memory. It is a finger pointing at one row on the server, and next() moves the finger.

  • The default is TYPE_FORWARD_ONLY and CONCUR_READ_ONLY: one pass, no going back, and no way to change a row through the cursor. Scrollable and updatable types exist, and they cost memory on the server.

One Statement, one open cursor.

one statement, two queries

     ResultSet a = s.executeQuery("SELECT id FROM account")) {

            "SELECT COUNT(*) FROM txn WHERE account_id = "

     PreparedStatement inner = c.prepareStatement(
         "SELECT COUNT(*) FROM txn WHERE account_id = ?");
     ResultSet a = s.executeQuery("SELECT id FROM account")) {
    while (a.next()) {
        inner.setLong(1, a.getLong(1));
        try (ResultSet t = inner.executeQuery()) { ... }

Reading typed values without lying.

The Java type int has no null, so something has to give. What it gives is a zero and a flag.

mapping / guess first

Where should "row to object" live?

Every query that touches account reads id, owner and balance_cents and builds an Account. Copy-pasted into every method? Inside an Account(ResultSet) constructor, so the domain object knows SQL? Or one small function per table, handed to a generic helper?

  • One function per table. And a function you can pass around is an instance of a one-method interface, which is all a lambda ever is.
  • One word first, because the next line turns on it. SQLException is checked: the compiler forces every caller either to catch it or to declare throws SQLException and pass the problem up.
  • And here is the rule that decides today's design: a lambda may only throw the checked exceptions its interface's method declares.

Function<ResultSet, String> f = rs -> rs.getString("owner");
// error: unreported exception SQLException; must be caught or declared to be thrown

Function.apply declares nothing, so java.util.function is useless for anything that touches JDBC. That is why every JDBC library on earth declares its own row mapper interface. Effective Java, Item 71

mappingthe interface
the move

RowMapper: one function per table, a record per row.


record Account(long id, String owner, long balanceCents) { }
@FunctionalInterface
interface RowMapper<T> { T map(ResultSet rs) throws SQLException; }
static Account toAccount(ResultSet rs) throws SQLException {
    return new Account(rs.getLong("id"), rs.getString("owner"), rs.getLong("balance_cents"));
}
static <T> List<T> query(Connection c, String sql, RowMapper<T> m, Object... args)
        throws SQLException {
    try (PreparedStatement ps = c.prepareStatement(sql)) {
        for (int i = 0; i < args.length; i++) ps.setObject(i + 1, args[i]);
        try (ResultSet rs = ps.executeQuery()) {
            List<T> out = new ArrayList<>();
            while (rs.next()) out.add(m.map(rs));  return out;
        }
    }
}
  • Calling it: query(c, "SELECT ... WHERE balance_cents > ?", Demo::toAccount, 5000L). RowMapper<T> is Function<ResultSet,T> with the one thing Function lacks: a throws clause.
  • The mapper is the only place that knows a column name, and it is handed into the query method, so the helper itself knows nothing about accounts. You have just written JdbcTemplate.query(sql, rowMapper, args) by hand.

architecture / the driver's job

Four kinds of driver. Only one of them still matters.

A driver is a jar that implements java.sql.Driver and friends, and turns your interface calls into that vendor's wire protocol.

TypeWhat it isWhere it lives now
1JDBC-ODBC bridge, native ODBC underneathremoved from the JDK in Java 8. Dead.
2thin Java over a vendor C libraryyou must install the client. Oracle OCI is the survivor.
3talks to a middleware server, which talks to the databasehistorical.
4pure Java, speaks the database's own protocol over a socketone jar, no install: h2, postgresql, mysql-connector-j, ojdbc11.
  • A driver implements Driver, Connection, Statement, PreparedStatement, CallableStatement and ResultSet. That is all it is.
  • It is a runtime dependency. Your code never imports it.
  • A driver that does not recognise your URL returns null and says nothing, which is how several of them live on one classpath.

driver loading / guess first

How does DriverManager find a driver it has never heard of?

You never wrote new org.h2.Driver() and you never named H2 in code at all. Does something scan the classpath, does the URL carry the class name, or does the jar say who it is?

  • The jar says who it is. Since JDBC 4.0 every driver ships one text file, META-INF/services/java.sql.Driver, holding its Driver class name.
  • Your first getConnection runs ServiceLoader.load(Driver.class) once, builds each class named in those files, and each one registers itself. Then getConnection(url) walks the registered drivers in order and asks connect(url, props). Not yours? Return null. First non-null wins, and all null gives you No suitable driver found.

the fine print

Class.forName, and the global that outlives your app.

  • Class.forName("org.h2.Driver") is the pre-2006 trick: it initialised the class, whose static block called DriverManager.registerDriver.
  • Today it is redundant, and since registration is lazy all it does is make registration happen earlier. You will see that line in every tutorial older than you are: it is a tell, not a bug.
  • A class initialiser runs at most once, so it cannot register twice. getDrivers() still shows one H2 driver.

the move

The transfer, done right.

The table itself carries CHECK (balance_cents >= 0): a rule the database enforces against every program, in any language.


static void transfer(Connection c, long from, long to, long cents) throws SQLException {
    c.setAutoCommit(false);
    try (PreparedStatement debit = c.prepareStatement(
             "UPDATE account SET balance_cents = balance_cents - ? WHERE id = ?");
         PreparedStatement credit = c.prepareStatement(
             "UPDATE account SET balance_cents = balance_cents + ? WHERE id = ?")) {
        debit.setLong(1, cents);  debit.setLong(2, from);
        if (debit.executeUpdate() != 1) throw new NoSuchAccountException(from);
        credit.setLong(1, cents); credit.setLong(2, to);
        if (credit.executeUpdate() != 1) throw new NoSuchAccountException(to);
        c.commit();
    } catch (Exception e) {
        c.rollback();  throw e;
    } finally { c.setAutoCommit(true); }
}
  • Catch Exception, not SQLException. That finally is a commit in disguise, so any unchecked exception escaping the catch leaves setAutoCommit(true) to make the half-done debit durable.
  • So an overdraft makes the debit throw and the catch rolls back. Two of those programs on the last picture can both pass the same if in Java at the same instant. Neither one can get past the CHECK.

the fine print

The shape every transaction method shares.

written once, body injected 

interface TxBody<T> { T run(Connection c) throws SQLException; }
static <T> T inTransaction(Connection c, TxBody<T> body) throws SQLException {
    c.setAutoCommit(false);
    try {
        T r = body.run(c);
        c.commit();
        return r;
    } catch (Throwable t) {
        try { c.rollback(); } catch (SQLException r) { t.addSuppressed(r); }
        throw t;
    } finally { c.setAutoCommit(true); }
}
  • Begin, work, commit, else roll back, always reset. Write it once and hand it the body: Day 1's template method with a lambda instead of a subclass, and it catches Throwable because this helper is the one place that can guarantee the rollback.
  • Here is the hole in it. Call one of these helpers from inside another and the inner commit() ends the outer transaction early, committing half its work. Spring has a setting for exactly that case, and the setting is called propagation.
  • Savepoint sp = c.setSavepoint(); ... c.rollback(sp); undoes part of a transaction and keeps the rest.

the answer, part 1

Isolation levels: what one transaction may see of another.

  • A dirty read sees another transaction's uncommitted work.
  • A non-repeatable read means the same SELECT gives a different value the second time.
  • A phantom means the same SELECT returns a new row the second time.
LevelDirtyNon-repeatablePhantomCost, and who defaults to it
READ_UNCOMMITTEDallowedallowedallowedlowest, and nobody's default
READ_COMMITTEDnoallowedallowedlow. PostgreSQL, Oracle, SQL Server, H2.

the answer, part 2

The lost update, frame by frame.

  • Read, compute in Java, write is not atomic even inside a transaction, because the database only serialised the two writes.
  • A row lock is the database making every other writer of that one row queue until the holder commits. The UPDATE took one. At READ_COMMITTED the plain SELECT took none, which is why T2 sat there holding a number that had already changed. Not a database bug and not a Java bug: your SELECT made a promise it could not keep.
isolationlost update
the fixes

Three ways to stop losing it, and which one to reach for.


// 1. atomic: the read and the write are one statement
UPDATE account SET balance_cents = balance_cents + ? WHERE id = 1;

// 2. pessimistic: the second read blocks until the first transaction commits
SELECT balance_cents FROM account WHERE id = 1 FOR UPDATE;

// 3. optimistic: write only if nobody moved, then retry when 0 rows matched
UPDATE account SET balance_cents = ?, version = version + 1
 WHERE id = 1 AND version = ?;

atomic SQL

balance = balance + ?. The best fix whenever the new value is a function of the old one, because there is no read to go stale. Counters, balances, stock levels.

SELECT ... FOR UPDATE

For when you must read, decide in Java, then write. It holds the row lock for the rest of the transaction, so keep that short, and lock rows in a consistent order.

version column

Read the version, write WHERE version = ?, retry when 0 rows come back. No lock is held while a human thinks. This is exactly JPA's @Version.

  • Deadlock, concretely: transfer(1,2) at the same instant as transfer(2,1) leaves each side holding one row and waiting for the other. Touch the lower id first, whichever direction the money is going.
  • SERIALIZABLE is the fourth option, correct by construction, but now you catch 40001 and retry. The capstone uses fix 1 plus a CHECK constraint.

callable / guess first

The logic already lives in the database. How do you call it?

  • A database can hold named programs of its own, written in its own language and run inside it. Somebody else usually owns them: the DBA, the database administrator. Your job is to call one and read what it hands back.
  • CallableStatement extends PreparedStatement, so binding works as it always has. You make one with c.prepareCall("{call transfer_funds(?, ?, ?, ?)}"), and those curly braces are JDBC escape syntax: the portable spelling of a call.
  • A procedure is called for its effect and answers through OUT parameters. A function returns one value and can be used inside ordinary SQL, where a plain PreparedStatement does the job.
  • IN is an input, like any ? today. OUT is an output, and you declare its type in advance. INOUT is both.

pooling / the javax.sql.DataSource

500 requests a second. How many handshakes is that?

Each request opens a Connection, runs two queries and closes it. That is 500 handshakes a second at 20 ms each, plus the database creating and destroying 500 sessions a second.

  • A DataSource is an object with getConnection(), so you can inject it, configure it outside your code and swap it in a test. None of that is true of a static DriverManager.
  • A pooling DataSource keeps N real connections open and hands out thin wrappers. close() on the wrapper does not close the socket, it returns the connection, and getConnection() costs microseconds instead of a handshake.

optional / guess first

findById finds nothing. What do you return?

Your query helper returns a List, the caller wants exactly one account by id, and there is no row with that id. The signature promises an Account. Null? An exception? An empty list?

  • Returning null is the exact bug Optional was invented to prevent: the type says Account, the value says nothing, and the NullPointerException arrives three stack frames away. Optional<Account> says maybe in the signature, so the compiler makes the caller decide.
  • Chain without unwrapping: repo.findById(id).map(Account::balanceCents).orElse(0L). orElse gives a default, orElseGet takes a Supplier, and orElseThrow(() -> new NotFoundException(id)) is what a web layer usually wants.
  • The trap worth memorising: orElse evaluates its argument eagerly, every single time, even when the Optional is present. orElse(expensiveDefault()) runs the expensive call on the happy path too. orElseGet(() -> expensiveDefault()) does not. That is Item 55.
  • Never call get() without isPresent(), and preferably never call get() at all. Never make an Optional a field, a parameter or a collection element: it is a return type, and an Optional<List> is always a bug. Return an empty list.
  • When you meet Spring Data, findById returns Optional<T>, and now you know why. The capstone's repository returns it too.

    Account save(Account a);               long count();

final class JdbcAccountRepository implements AccountRepository {
    private final DataSource ds;                       // set in the constructor
    public Optional<Account> findById(long id) {
        try (Connection c = ds.getConnection();
             PreparedStatement ps = c.prepareStatement(
                 "SELECT id, owner, balance_cents FROM account WHERE id = ?")) {
            ps.setLong(1, id);
            try (ResultSet rs = ps.executeQuery()) {

        } catch (SQLException e) { throw new RepositoryException("findById " + id, e); }

}

  • a DataSource bean that is a Hikari pool, configured in a properties file

None of that is magic. It is your afternoon, with better error messages.

the honest segue

And then there are ORMs, which are a bigger promise.

  • JPA and Hibernate go further than JdbcTemplate: you annotate a class and they write the SQL and the mapping for you, in both directions.
  • What you pay: N+1 by accident because a field access can be a query, lazy initialisation exceptions because that access happens after the session closed, a first-level cache you did not ask for and must reason about anyway, and SQL you did not write turning up in your slow query log at two in the morning.
  • JDBC is still underneath every one of them. The pooled Connection is still the resource, the transaction is still the boundary, and when the ORM misbehaves, everything you learned today is how you debug it.
  • Use an ORM for CRUD on a well-shaped model, drop to JdbcTemplate or plain SQL for reports and bulk work, and never let a tool stop you reading the statement it sent.

Tomorrow is servlets: the HTTP half of the same request. This repository gets a server in front of it, and a composition root that wires the DataSource, the repository and the service in one place.

what to actually remember

Ten lines, the whole day.

  • The driver is a Type 4 jar found by ServiceLoader, never named by you. H2 to MySQL is a URL and a jar.
  • A Connection is a socket, a session and a transaction. It is not thread-safe, and it owns every Statement and cursor you make from it.
  • SQL is code and values are data. A ? keeps them apart, and it can never bind an identifier.
  • A ResultSet is a cursor: next() first, wasNull or getObject(Class) for nulls, and one Statement holds one open cursor, so a nested query kills its sibling.
  • Every handle is a resource: try-with-resources, reverse order, suppressed exceptions kept.
  • Autocommit is on until you say otherwise, and setAutoCommit(true) commits an open transaction, so catch wider than SQLException.
  • READ_COMMITTED permits the lost update. The fixes are atomic SQL, FOR UPDATE, or a version column.
  • Batch plus one transaction plus named generated keys is every import you will write, and prepareCall("{call ...}") with registerOutParameter is how you call somebody else's procedure.
  • A DataSource is injected, and a pool makes close() a return, which is why you reset what you changed.
  • One repository per table, SQL in one place, Optional for the missing row, exceptions translated at the door.

The database is shared,
remote and slow.
Treat it that way.

Shared, so isolation and constraints are not optional, and your Java if is not a lock. Remote, so every round trip and every open socket is a cost somebody else pays for. Slow, so batch, pool, push the filter down, and ask for exactly what you need. Everything a framework adds is a wrapper around those three facts.
