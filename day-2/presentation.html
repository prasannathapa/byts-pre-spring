hierarchy / question, then the answer

Where does ArrayList actually sit?

Draw it from memory first. What is above ArrayList, what is above HashMap, and is Map a Collection? Most people put it there. It is not, and here is why: two trees, not one.

  • Map is not a Collection. A Collection holds elements; a Map holds pairs. Force Map under Collection<Entry> and add and contains stop meaning anything sensible: add what, an entry whose key is already there?
  • The Sorted and Navigable interfaces are where the good methods live: first, last, floor, ceiling, headMap, subMap. If you never look there, you write a loop instead.
  • Collections and Arrays are utility classes full of statics. They are not types in the tree, and nothing implements them.

list / question, then the answer

ArrayList or LinkedList: faster to insert at the front?

Hands up for LinkedList. It is O(1) and the textbook is right about the pointer. Now the question that decides it: how do you reach the front, holding a List and not a node? One contiguous array beats a chain of boxes.

  • get(i) on an ArrayList is one multiply and one load. On a LinkedList it walks i nodes, and each node is somewhere else in memory.
  • Adding at the end is amortised O(1) for both. Inserting in the middle is O(n) for both, because LinkedList has to walk there first, and walking is the expensive half.
  • The one honest LinkedList win is a ListIterator you already hold in the middle. Want both ends? That is a Deque, and ArrayDeque wins there too. So: ArrayList, until you can name the reason.

A HashSet of Points. Add (1,2) twice. How many?

Two. Add a correct equals and only equals, and it is still two, because a HashSet hashes before it ever asks equals.

  • Reflexive. x.equals(x) is true.
  • Symmetric. If x.equals(y) then y.equals(x). Day 1 watched java.sql.Timestamp break this against java.util.Date, in the JDK, still shipping.
  • Transitive. x to y to z, all the way through.
  • Consistent. Same answer every call, as long as nothing changed.
  • And x.equals(null) is false, never a NullPointerException.
  • Records generate all of this from their components, correctly, for free.

You cannot add a field to an instantiable class and keep equals.

Effective Java, Item 11

hashCode: equal objects, equal hashes. Always.

  • The contract is one line: if a.equals(b) then a.hashCode() == b.hashCode(). The reverse is not required. Collisions are legal, just slow.
  • Use the same fields as equals. Never more, never fewer.
  • 31 * result + c for each significant field. 31 is an odd prime, and 31 * i compiles to (i << 5) - i.
  • Objects.hash(x, y) is right for almost everything and wrong in a hot-path hashCode: it boxes every argument and allocates an Object[] on every call. Item 11 says so in those words.
  • For an array field, Arrays.hashCode(a) with Arrays.equals(a, b). An array's own hashCode is identity-based, which is the concrete reason never to use an array as a key.

// fine almost everywhere
return Objects.hash(x, y);

// no boxing, no array: for hot paths
int h = Integer.hashCode(x);
h = 31 * h + Integer.hashCode(y);
return h;

Verified on 25: Double.NaN != Double.NaN, yet Double.valueOf(NaN).equals(NaN) is true. And -0.0 == 0.0, yet the two are not equals. So a HashSet<Double> holds both -0.0 and 0.0, and List.of(NaN).contains(NaN) is true while == says false. That is the honest reason for Double.compare.

hashmap internals / question, then the answer

Where in the table does the key "Ravi" go?

How many buckets does a brand-new map have? Hands for 16, for 32, for zero. And "Ravi".hashCode() is 2539842, so which slot? It is one array of buckets, each a chain of nodes.

  • Every node caches its own hash, so a resize never calls your hashCode again.
  • The chain is where equals gets called, and nowhere else.
hashmapanatomy
the path of one put

put, line by line.


// 1. spread the high bits down, so a small table still uses them
static int hash(Object key) {
    int h; return key == null ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
// 2. empty bucket? just put a node there and go
if ((p = tab[i = (n - 1) & hash]) == null)
    tab[i] = newNode(hash, key, value, null);
else {
    // 3. walk the chain. int compare first, then identity, then equals
    if (p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k))))
        e = p;                                  // found it
    else { /* append to the tail; treeify if the bin got long */ }
    // KEY ALREADY THERE: overwrite and leave. Not structural, so no modCount, no size.
    if (e != null) { V old = e.value; e.value = value; return old; }
}
++modCount;                                     // NEW NODE only
if (++size > threshold) resize();
// "Ravi": 2539842 ^ (2539842 >>> 16) = 2539876, & 15 = bucket 4

get, the load factor, and when size > threshold

Resize: double the table, split every bucket in two.

  • get spreads the same hash, masks to the same bucket and walks the same chain, which is exactly why a key whose hashCode changed can never be found again. Load factor 0.75 keeps the average chain under one node, and that is what "O(1) expected" means.
  • Capacity and threshold both double, and not one hashCode runs, because each node cached its hash on the way in. Resize is O(n), which is why put is amortised O(1) but a single put can be slow.
  • So pre-size a large map, and know what the argument means: it is table capacity, not an entry count. For n entries pass (int)(n / 0.75f) + 1, or call HashMap.newHashMap(n) on Java 19 and later.
hashmapget, 0.75, resize
the Java 8 change

Treeify: when a chain gets long, it becomes a red-black tree.

  • A bin is treeified when a ninth node is appended to a bin that already holds eight. TREEIFY_THRESHOLD is 8 and putVal tests binCount >= 7. Verified on JDK 25: eight all-colliding keys is still a plain Node chain, and the ninth put makes it a TreeNode.
  • And only if the table has at least 64 slots (MIN_TREEIFY_CAPACITY). Below that the map resizes instead, because a small table collides for a boring reason. A tree bin turns back into a chain at 6 during a resize.
  • Worst case drops from O(n) to O(log n) when the colliding keys are Comparable or their hashes differ. Keys with identical hashes that are not Comparable still get a linear search inside the tree bin: the class-name tie-break only decides where a node is placed, not how find navigates. That is why String keys tree well.

the mutated-key trap

The key you mutated is still in the map. You just cannot reach it.


class Point { int x, y; /* correct equals and hashCode on x and y */ }

Set<Point> s = new HashSet<>();
Point p = new Point(1, 2);
s.add(p);
p.x = 5;                                      // one field. That is all it took.

s.contains(p);                                // false
s.remove(p);                                  // false
s.size();                                     // 1
for (Point q : s) System.out.println(q);      // (5,2)
  • The node's cached hash is stale. contains and remove hash the new state, so they look in a different bucket, and the p.hash == hash test would fail even if they landed in the right one.
  • It is not unreachable, though. The iterator walks the table and never hashes anything, so iterator.remove, removeIf, retainAll and clear all see it. Set p.x back to 1 and the key is findable again.
  • Item 17, minimise mutability. And the Map Javadoc simply says behaviour is unspecified if a key changes in a way that affects equals. Unspecified means nobody is going to help you.

composition / question, then the answer

InstrumentedHashSet: how many after addAll of three?


class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override public boolean add(E e) {
        addCount++;
        return super.add(e);
    }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }
}
s.addAll(List.of("Snap", "Crackle", "Pop"));
s.getAddCount();   // ?

Six. HashSet.addAll calls add, and nobody told you.

  • HashSet inherits AbstractCollection.addAll, which loops and calls this.add(e). this is your object, so that is your override. Three from addAll, three from add.
  • That self-use is an implementation detail. It is not in the Javadoc, and it can change in the next release without anyone calling it a break.
  • Delete your override and you are correct only while that detail holds. Reimplement without super and you redo it every release, and a new superclass method walks past your counter.
  • Inheritance across a package boundary breaks encapsulation: the subclass depends on the superclass's implementation, not its contract. That is Item 18 in one sentence.

Effective Java, Item 18: the forwarding class

Write the boring wrapper once.


class ForwardingSet<E> implements Set<E> {
    private final Set<E> s;
    ForwardingSet(Set<E> s) { this.s = s; }

    public boolean add(E e)           { return s.add(e); }
    public boolean remove(Object o)   { return s.remove(o); }
    public boolean contains(Object o) { return s.contains(o); }
    public int size()                 { return s.size(); }
    public boolean isEmpty()          { return s.isEmpty(); }
    public Iterator<E> iterator()     { return s.iterator(); }
    public void clear()               { s.clear(); }
    // ... and every remaining Set method forwards exactly like that
}
  • It implements the interface and holds an instance. So it depends on the Set contract and on nothing else. No detail can leak, because there is no superclass to leak from.
  • Yes, it is tedious. It is also written once, and capstone part 2 makes you finish five of these methods so the tedium is not theoretical.
  • Collections.unmodifiableSet and synchronizedSet are this class with one behaviour changed.

Effective Java, Item 18: composition

Wrap it, do not extend it.


class InstrumentedSet<E> extends ForwardingSet<E> {
    private int addCount;
    public InstrumentedSet(Set<E> s) { super(s); }

    @Override public boolean add(E e) { addCount++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size(); return super.addAll(c);
    }
    public int getAddCount() { return addCount; }
}

new InstrumentedSet<>(new HashSet<>()).addAll(List.of("a","b","c"));   // count: 3
  • super.addAll forwards to the wrapped set. Its internal add calls go to that object and never come back to us. Three.
  • One InstrumentedSet wraps any Set: a HashSet, a TreeSet, a synchronizedSet, something you have not written yet. A subclass of HashSet could never do that.
  • This is the Decorator pattern from Day 1, and the one real cost is worth naming: a wrapper is not suited to callback frameworks, because the wrapped object passes itself to the callback, not the wrapper. That is the SELF problem.

linkedhashmapanatomy
the move: accessOrder + removeEldestEntry

An LRU cache in six lines.


class LruCache<K,V> extends LinkedHashMap<K,V> {
    private final int capacity;
    LruCache(int capacity) { super(16, 0.75f, true); this.capacity = capacity; }

    @Override protected boolean removeEldestEntry(Map.Entry<K,V> eldest) {
        return size() > capacity;
    }
}

LruCache<String,Integer> cache = new LruCache<>(2);
cache.put("a", 1); cache.put("b", 2);
cache.get("a");                 // "a" is now the most recent
cache.put("c", 3);              // over capacity: the eldest goes
cache.keySet();                 // [a, c]
  • Note what changed since the InstrumentedHashSet slide: removeEldestEntry is a protected hook whose Javadoc describes this exact use. Here extension is the contract, not a leak. That distinction is the whole of Item 19.
  • get counts as an access. containsKey does not, which surprises people once and only once.
  • For a thread-safe one, wrap it in Collections.synchronizedMap or reach for Caffeine. Capstone part 2 has you build this.

the lambda Comparator has been asking for

A lambda is an instance of a one-method interface.


// 1. the anonymous class
Collections.sort(people, new Comparator<Person>() {
    @Override public int compare(Person a, Person b) { return a.name().compareTo(b.name()); }
});

// 2. List has its own sort, so the Collections call goes
people.sort(new Comparator<Person>() {
    public int compare(Person a, Person b) { return a.name().compareTo(b.name()); }
});

// 3. the target type is Comparator<Person>, so the compiler knows all of that
people.sort((a, b) -> a.name().compareTo(b.name()));

// 4. and there is a combinator for exactly this shape
people.sort(Comparator.comparing(Person::name));
  • The lambda is a Comparator. No new runtime concept, just a shorter way to write an instance of a one-method interface. a and b carry no types because the target type supplies them, and the target must be an interface, never an abstract class.
  • Four kinds of method reference, and step 4 uses one: Integer::parseInt is static, String::length is unbound so the argument becomes the receiver, ""::equals is bound so the receiver is fixed right now, and ArrayList::new is a constructor.

four traps in the combinators

Comparator: four ways to get this wrong, all of them quiet.


// 1. BOXING: comparing() needs a Comparable key, so the int is boxed on every extraction.
comparing(Person::age)        // boxes
comparingInt(Person::age)     // takes a ToIntFunction, allocates nothing

// 2. INFERENCE: this does not compile. javac infers Object for that first lambda:
//    "cannot find symbol: method name(), location: variable p of type Object"
list.sort(comparing(p -> p.name()).thenComparing(p -> p.age()));
list.sort(comparing(Person::name).thenComparing(Person::age));   // a method ref fixes it

// 3. reversed() REVERSES THE WHOLE CHAIN, not the last key:
comparing(P::name).thenComparingInt(P::age).reversed();            // name desc, THEN age desc
comparing(P::name).thenComparing(comparingInt(P::age).reversed()); // name asc, age desc

// 4. nullsFirst guards a null ELEMENT, not a null KEY:
nullsFirst(comparing(P::name));                  // still NPEs on a P with a null name
comparing(P::name, nullsFirst(naturalOrder()));  // the two-argument form is the fix

  • Verified here: 16 elements sorted quietly in 5000 runs out of 5000, and 1000 elements threw in 4999 of those 5000. It passes your five-element test and fires on the customer's data. The causes are always subtraction overflow, a field that changes during the sort, or forgetting that equal must mean 0.

A rota keyed by Day: HashMap, or something faster?

Faster, and it already ships: an array indexed by ordinal(), and a single long used as a bit vector.


Map<Day, List<Shift>> rota = new EnumMap<>(Day.class);   // needs the class: no other way

the heap

PriorityQueue: the smallest is at the head, and nothing else is in order.


PriorityQueue<Integer> pq = new PriorityQueue<>(List.of(4, 5, 1, 2, 3));
System.out.println(pq);                             // [1, 2, 4, 5, 3]  not sorted
while (!pq.isEmpty()) System.out.print(pq.poll());   // 12345            sorted on the way out

// top-k in O(n log k): a min-heap of size k, so the WORST entry is the one you drop
Comparator<Entry> worstFirst =
    Comparator.comparingInt(Entry::count).thenComparing(Entry::word, Comparator.reverseOrder());

PriorityQueue<Entry> heap = new PriorityQueue<>(worstFirst);
for (Entry e : entries) {
    heap.offer(e);
    if (heap.size() > k) heap.poll();   // evicts the head, which is the least wanted
}
  • offer and poll are O(log n), peek is O(1), and contains and remove(Object) are O(n) because a heap has no index.
  • toString and iteration walk the backing array, so they are never sorted. Only the head means anything. People lose an afternoon to this.
  • The size-k heap discards from the head, so its comparator must put the least wanted entry first. That means the tie-break runs backwards: if you want ties alphabetical in the result, the heap must order ties reverse-alphabetically, and then you drain and reverse. The finale uses exactly this, and the tie direction is the part people get wrong.
  • Not thread-safe. PriorityBlockingQueue is.

the Integer cache

Integer == Integer is true from -128 to 127. Then it is a coin you did not flip.


Integer a = 100, b = 100;   a == b;        // true   both came from the valueOf cache
Integer c = 1000, d = 1000; c == d;        // false  two separate objects
                            c.equals(d);   // true   equals compares the value
Short   e = 100;            a.equals(e);   // false  equals compares the TYPE first
                            a == e;        // does not compile: incomparable types
Integer f = 1000;           f == 1000;     // true, and this one is arithmetic, not identity
                                           // (the cache has nothing to do with it)
  • Autoboxing goes through Integer.valueOf, which caches -128 to 127. JLS 5.1.7 requires at least that range and the upper bound is tunable, so the exact cliff is not even a language guarantee.
  • == on two wrappers compares references. equals compares value and type, which is why an Integer is never equal to a Long however equal the numbers look.
  • Mix a wrapper and a primitive in one == and the wrapper is unboxed, so it becomes a numeric comparison. One primitive operand changes the meaning of the operator.
  • Inside a Map<Integer,...> none of this matters, because HashMap calls equals. In your own == it decides everything. Item 61: prefer primitives to boxed primitives, and remember remove(int) against remove(Object) from part 1.

iteration / question, then the answer

Remove "b" inside a for-each. Which line throws?

  • ArrayList keeps a modCount that every structural change bumps. The iterator copies it once into expectedModCount and compares the two inside next(). That is the only place the exception can come from.
  • hasNext() is just cursor != size. Remove the second-to-last element and size drops to meet the cursor, so hasNext answers false, next() never runs, and the loop ends quietly with [a, c]: no exception, and "c" was silently never visited.

List<String> l = new ArrayList<>(List.of("a", "b", "c"));

the move

Five safe ways to change what you are walking.


Iterator<String> it = l.iterator();               // 1. the iterator's own remove
while (it.hasNext()) if (it.next().equals("b")) it.remove();

l.removeIf(s -> s.equals("b"));                   // 2. a Predicate, one pass
l.replaceAll(String::toUpperCase);                // 3. a UnaryOperator, in place

m.entrySet().removeIf(e -> e.getValue() == 0);    // 4. maps: prune through the view
for (var e : m.entrySet()) e.setValue(0);         //    setValue is not structural: no CME

for (int i = l.size() - 1; i >= 0; i--) { ... }   // 5. backwards by index, or collect
                                                  //    the victims and removeAll after
  • removeIf on an ArrayList is one pass that marks its victims in a bit mask and compacts the array once, not n separate removes each shifting the tail. ListIterator.add and set edit in place. A CopyOnWriteArrayList never throws here at all, because its iterator holds a snapshot.

generics / question, then the answer

Is a List<Integer> a List<Number>?

No. An array says yes and blows up at run time. Arrays are covariant and reified; generics are invariant and erased.

  • Number[] arr = new Integer[1] compiles, and arr[0] = 3.14 throws ArrayStoreException at run time, because an array carries its element type with it and checks every store.
  • List<Number> nums = ints does not compile. If it did, nums.add(3.14) would drop a Double into a list of Integer and the erased List could not stop it. The compile error is the protection.
  • Erasure means List<Integer> and List<String> are one class at run time: no new T[], no instanceof List<String>.
  • Item 28, prefer lists to arrays, especially in an API. Item 26, never use raw types: a raw List has opted out of type checking. It is not List<Object>, which a List<String> cannot be assigned to either.

Effective Java, Item 31

PECS: producer extends, consumer super.


List<? extends Number> src = new ArrayList<Integer>();
Number n = src.get(0);     // fine: whatever is in there IS a Number
src.add(1);                // does not compile: src could be a List<Double>

List<? super Integer> dst = new ArrayList<Number>();
dst.add(1);                // fine: an Integer fits in any supertype list
Object o = dst.get(0);     // only Object comes out: we do not know the element type

static <T> void copy(List<? super T> dst, List<? extends T> src)   // both, in one signature
double sum(Collection<? extends Number> c)
Comparator<? super T>
static <T> T max(Collection<? extends T> c, Comparator<? super T> comp)
  • extends means you read from it, super means you write to it, and if you do both then no wildcard at all. That is the whole mnemonic and it is worth memorising.
  • This is why every combinator you met takes Function<? super T, ? extends R>: it lets a Comparator<Object> sort your Persons without you casting anything.
  • Do not put wildcards in return types. All it does is push the problem onto every caller.
  • A List<?> takes any list and lets you add exactly one thing: null.

Arrays.asList: fixed size, write-through, and it boxes nothing.

concurrency / question, then the answer

Two threads put into one HashMap. What is the worst that happens?

  • All four. Two unsynchronised writers can resize at once, lose entries and publish a half-built table. On Java 7 they could also build a cyclic chain, and a later get() would spin forever on one core.
  • Collections.synchronizedMap locks the whole map on every call: correct, slow, and no help at all for containsKey then put, because the lock is released between the two and the gap is where the race lives.
  • Since Java 8, ConcurrentHashMap installs a node in an empty bin with one CAS and synchronizes on the head node of a full one, so writers to different buckets never wait. The fix for check-then-put is one call: putIfAbsent, computeIfAbsent, compute and merge are atomic per key.

the two traps

merge has a delete branch you did not ask for.


Map<String,Integer> cart = new HashMap<>(Map.of("apple", 3, "pear", 7));

cart.merge("apple", 3, (old, taken) -> old - taken == 0 ? null : old - taken);
//   present, function returns null -> the MAPPING IS REMOVED. apple is gone.
cart.merge("pear",  2, (old, taken) -> old - taken);            // present  -> pear = 5
cart.merge("plum",  4, (old, taken) -> old - taken);            // ABSENT   -> plum = 4,
//   the function never ran. It would have computed -4.
cart.merge("pear", null, (a, b) -> a);                          // NullPointerException

Map<String,Integer> m = new HashMap<>();
m.computeIfAbsent("a", k -> { m.put("b", 1); return 1; });  // ConcurrentModificationException
m.computeIfAbsent("a", k -> null);                          // returns null, STORES NOTHING
  • For an absent or null-mapped key, merge stores the value argument as it is and never calls the function. So a remapping function with a side effect only runs for keys that already exist, and that asymmetry is the bug.
  • For a present key the function runs with (oldValue, value) and its result is stored, except that null means remove. And the value argument itself must be non-null, so you cannot delete by merging a null either.
  • compute and computeIfPresent follow the same null-means-remove rule, so a counting map built on merge can shrink while you believe you are only decrementing.
  • computeIfAbsent's function must not modify the same map. Since Java 9 a HashMap throws a fast CME instead of Java 8's silently corrupted table, and the usual way in is a memoised Fibonacci. On a ConcurrentHashMap it can deadlock: the bin is locked while your function runs. All verified on 25.

the three views

keySet, values and entrySet are the map, not copies of it.


Map<String,Integer> m = new HashMap<>(Map.of("a", 1, "b", 2));

m.keySet().remove("a");        // the MAPPING is gone. m is {b=2}
m.keySet().add("c");           // UnsupportedOperationException, always: no value to store
m.values().remove(2);          // removes ONE mapping with that value, whichever comes first

m.entrySet().removeIf(e -> e.getValue() == 0);            // the idiom for pruning a map
for (var e : m.entrySet()) e.setValue(e.getValue() + 1);  // write-through, not structural

Map.entry("a", 1).setValue(2);                            // UnsupportedOperationException
  • All three are backed by the map. A removal writes through, and an addition is impossible, because a key with no value has no meaning.
  • That is why entrySet().removeIf is the safe way to prune, and why the fail-fast rules from earlier apply to the views exactly as they apply to the map.
  • An Entry from entrySet() is a handle on the map, not a value you own: setValue writes into the map, and it is the only mutation it supports.
  • The entries of Map.of, and anything from Map.entry, are immutable, so setValue throws. If you need to keep entries around, copy them with Map.entry(e.getKey(), e.getValue()). Verified on 25.

filter, map, toList: the useful 10 percent.


List<String> longNames = people.stream()

The Optional below is present. Call the last two lines in a loop ten times: how many times does expensive() run? Hands for zero, hands for ten. Then count what Java has to evaluate before it enters the method.


Optional<Version> v = registry.latest();

  • The counting-supplier test was orElseGet being lazy. That is the Optional slide with a test around it: orElse evaluates its argument even when the value is there, so that version failed.
  • Part 2. InstrumentedHashSet == 6 is Item 18 self-use. InstrumentedSet == 3 is forwarding. Same behaviour requested, two answers, and the five methods you wrote by hand are why Bloch calls a forwarding class tedious and reusable, in that order.
  • The wrapped-TreeSet test is the whole argument in one line: a wrapper is not a subclass, so it works over any Set.
  • The LRU tests are accessOrder and removeEldestEntry. If eviction ignored your get, the constructor flag was false.
  • Finale. merge is counting, and its null branch is deleting. computeIfAbsent is grouping. The heap is top-k in O(n log k) with the tie-break reversed.
  • mostFrequent is Optional. words() is stream.toList() being unmodifiable. And copyOf against unmodifiableMap is snapshot against view, which is the test most people fail first.

what to actually remember

Fourteen lines, the whole day.

  • Map is not a Collection. Declare the interface, construct the class (Item 64).
  • ArrayList by default. LinkedList almost never.
  • equals and hashCode together, over the same fields, and those fields immutable (Items 10, 11).
  • HashMap is: spread the hash, (n-1) & hash, walk the chain, call equals, resize at 0.75, treeify on the ninth node once the table has 64 slots.
  • Never mutate a key. Wrap it, do not extend it (Item 18).
  • LinkedHashMap for order, and for an LRU. TreeMap believes compareTo and nothing else (Item 14).
  • A lambda is an instance of a one-method interface, and the four shapes are Predicate, Function, Consumer, Supplier.
  • merge returning null deletes the entry. computeIfAbsent must not touch its own map.
  • List.of is immutable and null-hostile. unmodifiableX is a view. Arrays.asList is fixed size.
  • Fail-fast is best-effort, so use removeIf.
  • PECS, and no raw types (Items 31, 26).
  • ConcurrentHashMap, and the per-key atomics.
  • orElse evaluates its argument, orElseGet does not (Item 55). stream.toList() is unmodifiable.
  • Return empty, never null (Item 54).
