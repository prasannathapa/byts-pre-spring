first, the point of all of it

Two names for one goal.

OOP exists to manage complexity: cut a big program into objects with boundaries. SOLID exists to keep those boundaries sharp, so you can change code without fear.

day 1the point
pillar 1 / encapsulation

What does one public field cost you?

It looks free. It is the most expensive line in the file.

encapsulationquestion
the answer

A public field is a promise you can never take back.

  • Anyone can read it and write it, from anywhere.
  • So you can never add a rule later, like "a balance can't go negative", without breaking every caller that touched it.
  • You use a microwave with a button. You do not open it and rewire the magnetron. That barrier is the feature.
encapsulationwhy
the move, and the leak nobody counts

Hide the state. Expose the behaviour.

exposed 

class Account {
    public double balance;
}
// anyone: acc.balance = -999;
guarded 

class Account {
    private double balance;
    void withdraw(double amt) {
        if (amt > balance) throw ...;
        balance -= amt;
    }
}
three keywords that read like a lock 

public static final String[] SUITS = { "clubs", "hearts" };
SUITS[0] = "oops";   // legal, and global
actually locked 

private static final String[] SUITS = { "clubs", "hearts" };
public static final List<String> SUITS_VIEW = List.of(SUITS);

A non-zero-length array is always mutable, whatever you write in front of it. The rule under both pairs: if a caller can reach your state without calling one of your methods, you have no invariant, only a hope.

Effective Java, Items 15 and 16
encapsulationhow
the trap everyone falls into

Getters and setters are not encapsulation.

A setter for every field is just a public field with three extra lines. Ask what the object can do, not what fields it has.

Do not pull an object's data out to act on it. Tell the object to act. Tell, don't ask.

encapsulationtell, don't ask
the strongest version, and the rule

State that cannot change cannot be corrupted.

If a value never changes after it is built, there is nothing to guard. Make fields final, offer no setters.

Java records give you an immutable value for free: fields, constructor, equals, all done.


record Money(long cents, String currency) { }
  • Private by default.
  • Expose behaviour, not data.
  • Copy or wrap anything you hand out, and that includes a Map you return. The capstone Ledger has a test for exactly that leak.

The JDK's own java.util.Date is the cautionary tale here. We open it up in the hall of shame.

encapsulationimmutability + rule
the version of that rule everyone gets wrong

A record is shallowly immutable. That is all.

a hole with a final keyword on it 

record Team(String name, List<String> members) { }

Team t = new Team("core", members);
t.members().add("cy");
// the caller just edited your record, and the
// generated equals now changes over time
copied on the way in 

record Team(String name, List<String> members) {
    Team {
        members = List.copyOf(members);
    }
}
// and the accessor hands back a list
// nobody can write through
  • final protects the reference, never the object it points at.
  • Copy on the way in and on the way out. One alone is still a hole.
  • When the parameter type can be subclassed, use a constructor or a static factory, never clone(): the caller's subclass decides what clone returns.

pillar 2 / abstraction

A map is not the territory. So what do you leave off the map?

A map that shows every blade of grass is useless. Its value is what it leaves out.

abstractionquestion
the answer

Abstraction is deciding what to ignore.

  • A good abstraction shows the essentials and hides the mechanism.
  • You drive with a wheel and a pedal. You are not thinking about combustion.
  • The wheel is the abstraction: the simple idea you touch, standing in for the complicated thing underneath.
  • People mix this up with encapsulation. Encapsulation hides data: who may touch this state? Abstraction hides mechanism: what is the simplest idea I can hand the caller? You ask both, constantly.
abstractionwhy
the move, in Java

Name what it can do. Say nothing about how.

An interface is a promise: these operations exist. It says nothing about the implementation.


interface PaymentGateway {
    Receipt charge(Money m);
}

// depend on the promise:
PaymentGateway gw =
    new StripeGateway();

Program to the interface. Swap the implementation, and the caller never notices.

Default to interfaces. Reach for an abstract class only when several types share real implementation, not just a shape.

abstractioninterface vs abstract
the rule

Abstract carefully, and late.

Duplication is far cheaper than the wrong abstraction.

Sandi Metz

  • Name the capability, not the class. PaymentGateway, not StripeHelper.
  • Return the interface, not the concrete type.
  • Do not abstract until you have seen the duplication at least twice. Guessing wrong is expensive.
abstractionchecklist
the promise you make for code you have never seen

A default method lands in every implementer, uninvited.

count=6 data=3 

interface Sink {
    void add(String s);
    default void addAll(Collection<String> c) {
        for (String s : c) add(s);        // self-use
    }
}
class Counting implements Sink {
    public void addAll(Collection<String> c) {
        count += c.size();
        Sink.super.addAll(c);             // and add() counts again
    }
}
add nothing, publish a new type 

// you cannot fix Sink without breaking
// Counting, and Counting is not yours

interface BulkSink extends Sink {
    @Override void addAll(Collection<String> c);
}
  • A default method is a promise you make on behalf of code you have never seen.
  • You cannot test it against implementations that do not exist yet, so document the self-use or add nothing.
  • The real casualty was Collection.removeIf, which broke Apache Commons SynchronizedCollection.

pillar 3 / inheritance

The most dangerous tool in OOP. When is extends actually right?

It looks like free reuse. That is exactly why it bites.

inheritancequestion
why it bites

Inheritance welds a child to a parent's insides, forever.

  • A subclass depends not just on what the parent does, but on how.
  • Change the parent, and you can silently break every child. The fragile base class problem.
  • In 1996 the JDK 1.0 shipped java.util.Stack extends Vector, so every Stack has add(int, e), get(i), remove(i) and Vector's synchronisation.
  • Thirty years on, its own Javadoc tells you to use the Deque interface instead. It cannot be fixed: a public superclass is forever.
inheritancefragile base class
the mechanism, not the symptom

The parent runs first. Your fields do not exist yet.


class Base {
    Base() { init(); }                 // calls an overridable method
    void init() { }
}
class Sub extends Base {
    private String s = "ready";
    @Override void init() { System.out.println(s); }
}

new Sub();
  • The superclass constructor runs before any Sub field initialiser, so the override sees a field that has not been assigned yet.
  • The JDK does this to itself: Throwable() calls the public overridable fillInStackTrace(), which is why the cheap-exception trick works and why it is a documented hazard.
  • javac -Xlint:this-escape, JDK 21 and later, warns on exactly this shape: possible this escape before subclass is fully initialized.

The rule: if a class is not designed and documented for inheritance, make it final, or give it only private constructors and a static factory.

Effective Java, Item 19
inheritanceself-use
the test to apply

is-a, or has-a?

Use inheritance only for a true is-a that will never change: a Circle is a Shape.

Extending a class just to borrow its code is really a has-a. A Car is not an Engine; it has one.

inheritanceis-a vs has-a
the default you should reach for

Composition over inheritance.

the real JDK, inheriting the guts 

public class Stack<E> extends Vector<E> {
    E push(E e) { ... }
    E pop()     { ... }
}

Stack<String> s = new Stack<>();
s.add(0, x);   // legal
s.get(1);      // legal, and now it is not a stack
holds what it needs 

class Stack<E> {
    private final ArrayDeque<E> items
        = new ArrayDeque<>();
    void push(E e) { items.push(e); }
    E pop()        { return items.pop(); }
}

Compose by default, inherit on purpose, seal the family, and never inherit just to reuse code. A protected member is a promise to every subclass, so either document exactly when the parent calls it (read the implementation requirements notes on AbstractList) or make the class final.

The good side has a name: a forwarding class. You write one properly tomorrow, to fix a counting bug this exact shape causes.

when inheritance IS the right tool

A closed, known set of variants.

When a concept has a fixed family of shapes, inheritance is exactly right. Java's sealed types let you say so, and the compiler enforces it.


sealed interface Shape
    permits Circle, Square, Triangle { }

No rogue subclass can appear; a switch is checked for completeness.

pillar 4 / polymorphism

Different objects, same call. Why is that the whole point?

It is what lets you add new behaviour without editing old code.

polymorphismquestion
the answer

One call. Many behaviours. Chosen at runtime.

  • You call shape.area(). The right code runs based on what the object actually is.
  • The caller does not switch on type. The object already knows what to do.
  • That is dynamic dispatch, the engine under most OOP design.
polymorphismdynamic dispatch
the move, in Java

An interface, several implementations, one call.


interface Shape { double area(); }

record Circle(double r) implements Shape {
    public double area() { return Math.PI * r * r; }
}
record Square(double s) implements Shape {
    public double area() { return s * s; }
}

for (Shape s : shapes) total += s.area();   // no if, no switch

@Override is a contract you ask the compiler to check, not decoration. The next slide shows what it catches.

polymorphismin java
and what is not

Only instance methods are polymorphic.


class Base {
    static String kind() { return "base"; }
    String name()        { return "B"; }
    String tag = "b";
}
class Sub extends Base {
    static String kind() { return "sub"; }
    String name()        { return "S"; }
    String tag = "s";
}

Base x = new Sub();
System.out.println(x.kind() + " " + x.name() + " " + x.tag);
  • The method is chosen by the object. The field and the static are chosen by the declared type.
  • A same-named field hides, it does not override, and both fields exist in the object at once.
  • A private method is not a member of the subclass, so a same-signature method there is a new method, not an override (JLS 8.4.8).
  • Which overload runs is decided by the compiler from the static types of the arguments. Only the receiver is polymorphic.

Write @Override on every override and let the compiler tell you when you only thought you had one.

polymorphismwhat does not dispatch
why it matters

Open for extension. Closed for modification.

If you are switching on a type, stop. New behaviour is a new class, not a new branch in old code. Hold on to this slide: after the break it becomes the O in SOLID.

polymorphismopen/closed
a taste of tomorrow

Swap behaviour by swapping the object.

Hold an interface as a field, or take one as a parameter, and the class changes what it does with no edit anywhere.


names.sort(Comparator.comparing(String::length));
names.sort(Comparator.reverseOrder());
// same sort, different object handed in

That is the JDK's own example, and you meet Comparable and Comparator properly on Collections day, including why a comparator that disagrees with equals wrecks a TreeSet. People call this shape Strategy. The machinery is just polymorphism.

part 2 / from pillars to principles

You have the tools. Now, five habits to keep them sharp.

SOLID is five specific, checkable rules in service of one goal: code you can change without fear.

None of them are new. Two of them are literally the pillars you just met, polymorphism and abstraction, stated as design rules. SOLID is OOP done on purpose.

solidthe point
the five, at a glance

S O L I D.

Awful names. By the end, each is one plain sentence plus one smell you can spot on sight.

solidthe map
S / single responsibility

What makes a class need to change?

Not the number of methods it has. The number of people who can walk up and ask for one.

single responsibilityquestion
the outdated definition

"A class should do one thing" is wrong.

Run the test. Open ArrayList in the JDK: about sixty methods, add, remove, get, set, sort.

If the rule were "do one thing," ArrayList would be a disaster. Nobody splits ArrayList.

So "do one thing" cannot be the rule. A count of methods tells you nothing.

single responsibilitythe myth
the actual rule

Answer to one actor.

"A module should be responsible to one, and only one, actor."

Robert C. Martin, correcting fifteen years of misquotes

  • A "reason to change" is not a feature. It is a person, a role, a stakeholder whose request triggers the change.
  • CFO, HR, DBA: those are reasons. Bad classes are not bad for having many methods; they are bad when their methods answer to different people who never talk.

Hold that thought over the break. After it, we watch one class serve three masters and blow up.

single responsibilityone actor
the actor lens

Find the people. Then find their code.

  • One Employee class, three methods, three departments.
  • calculatePay() answers to the CFO. reportHours() answers to HR. save() answers to the DBA.
  • Accounting tweaks the pay math, reuses a shared helper, and HR's report quietly breaks. Nobody warned HR.
single responsibilitythe actor lens
before / after

Split the class along the actors.

three actors, one class 

class Employee {
  // CFO's rules
  Money calculatePay() { ... regularHours() ... }
  // HR's report
  String reportHours() { ... regularHours() ... }
  // DBA's schema
  void save() { ... }
  // shared helper = the hidden landmine
  int regularHours() { ... }
}
one actor each 

record Employee(String id, int worked) { }

class PayCalculator {        // CFO
  Money pay(Employee e) { ... }
}
class HourReporter {         // HR
  String report(Employee e) { ... }
}
class EmployeeRepo {         // DBA
  void save(Employee e) { ... }
}

Now the CFO's change touches only PayCalculator. HR's report cannot break from a payroll edit, because the shared helper is gone.

single responsibilitybefore / after
smell, and rule

Two teams in one file.

Smells

A class named Manager, Util, or Helper. A constructor with many collaborators. Imports from several unrelated namespaces. Two unrelated tickets touching it in one sprint.

Rule

One actor, one module. If two departments would edit this file for different reasons, it is two files in a trench coat.

Quick 30-second check: say what the class does in one sentence. If you need "and" (or a vague verb like "manages"), look again.

O / open-closed

A new feature arrives. Do you edit old code, or add new?

Editing working code is how you break things that used to work.

open-closedquestion
the answer, in code

From a switch to an interface.

closed to nothing 

String export(Report r, String type) {
  switch (type) {
    case "csv":  return toCsv(r);
    case "json": return toJson(r);
    // add "xml"? reopen this method,
    // and every other switch like it
  }
  throw new IllegalArgumentException(type);
}
closed for modification 

interface ReportFormat {
  String format(Report r);
}
class CsvFormat  implements ReportFormat { ... }
class JsonFormat implements ReportFormat { ... }

// a new format is a NEW class;
// export() is never reopened
String export(Report r, ReportFormat f) {
  return f.format(r);
}

This is exactly the capstone you build this afternoon, and it is this morning's polymorphism slide stated as a rule.

open-closedbefore / after
the picture, and the rule

A wall socket: fixed shape, endless appliances.

The socket is standard and closed. Any appliance whose plug fits just works, and you can invent new appliances forever. In code, the socket is an interface.

Smell

A switch or if-else on a type that grows a branch every time a variant is added. You keep reopening the same file.

Rule

Put the varying part behind an interface. A new case is a new class, not an edit to the old one.

L / liskov substitution

A subtype should work anywhere its parent does. When does that break?

When the child looks like the parent, but does not behave like it.

liskov substitutionquestion
the answer, before the code

In maths a Square is a Rectangle. In code it is a liability.

  • Rectangle's code makes a promise: set the width, and the height is left alone.
  • A Square cannot keep that promise and stay square. So it breaks the parent's contract, not the parent's syntax.
  • The compiler is perfectly happy. That is the whole point of this principle: it is the one you cannot delegate to javac.

The fix is not a cleverer Square. It is two types that do not inherit from each other.

liskov substitutionthe story
the classic trap, in code

The subtype that fails the parent's test.

looks right, lies 

class Rectangle {
  int w, h;
  void setW(int w){ this.w = w; }
  void setH(int h){ this.h = h; }
  int area(){ return w * h; }
}
class Square extends Rectangle {
  void setW(int w){ this.w = this.h = w; } // !
  void setH(int h){ this.w = this.h = h; } // !
}
void check(Rectangle r){
  r.setW(5); r.setH(4);
  assert r.area() == 20;  // FAILS for Square
}
don't force the is-a 

sealed interface Shape
    permits Rectangle, Square {
  int area();
}
record Rectangle(int w, int h) implements Shape {
  public int area(){ return w * h; }
}
record Square(int side) implements Shape {
  public int area(){ return side * side; }
}
// no inheritance to abuse; each keeps
// its own honest promise

The platform has its own version, two lines long: Object[] a = new String[1]; then a[0] = 42; compiles, and throws ArrayStoreException: java.lang.Integer at run time. Arrays are covariant and generics are not. Java had no generics until 2004 and Arrays.sort(Object[]) had to work, so the type system was told a lie in 1996 and we still live with it. Collections day owns the full treatment, Item 28, prefer lists to arrays.

liskov substitutionbefore / after
half of this is a compile error, half is not

Inherit the type, inherit the promises.

What the compiler already checks

An override cannot reduce visibility. It cannot add checked exceptions the parent did not declare. A return type may only narrow, never widen.

Smells

An override that throws UnsupportedOperationException. Callers checking instanceof to special-case a subtype. A subclass that quietly does nothing.

Rule

Usable through the parent's type with no surprises. If it cannot be, do not subclass. Compose instead.

Every check in the first card is Liskov, enforced. What no compiler can check is behaviour, which is why Square and Rectangle compiles perfectly and still fails the parent's test, and why an override that throws "not supported" is legal Java and a broken subtype.

@Override is the same idea in miniature: it asks the compiler to confirm you are keeping a promise rather than making a new one.

I / interface segregation

One big interface, or many small ones?

A big interface forces classes to depend on methods they never use.

interface segregationquestion
the answer, in code

Stop faking methods you don't have.

forced to lie 

interface Machine {
  void print(Doc d);
  void scan(Doc d);
  void fax(Doc d);
}
class SimplePrinter implements Machine {
  public void print(Doc d){ ... }
  public void scan(Doc d){
    throw new UnsupportedOperationException();
  }
  public void fax(Doc d){
    throw new UnsupportedOperationException();
  }
}
role-shaped 

interface Printer { void print(Doc d); }
interface Scanner { void scan(Doc d); }
interface Fax     { void fax(Doc d); }

class SimplePrinter implements Printer {
  public void print(Doc d){ ... }
}
class OfficeMachine
    implements Printer, Scanner, Fax {
  ...   // implement several when you are several
}

Split by role, and a class implements only what it is. Clients then depend on the slice they use, nothing more: the dead lying methods vanish, and a change to Fax can no longer force SimplePrinter to recompile.

interface segregationbefore / after
smell, rule, and the worst offender in the language

Methods you have to fake.

Smell

Implementers that throw or no-op half an interface. A client dragged into recompiling because a method it never calls changed.

Rule

Interfaces belong to their clients. Keep them small and role-shaped. A class can implement several.

The fattest interface in Java


public final native Class<?> getClass();
public native int hashCode();
public boolean equals(Object);
public String toString();
protected native Object clone();
protected void finalize();

javap java.lang.Object, and five more about thread coordination: wait, wait, wait, notify, notifyAll. Eleven methods on every object you will ever create.

  • Every class you write inherits a monitor and a wait/notify protocol it almost never uses, and you cannot opt out. That is what it costs when a type is defined once, at the top, for everyone.
  • The fewer clients an interface has, the smaller it should be. The root type has every client there is.

D / dependency inversion

Should your business logic depend on the database?

If it does, you cannot change the database, or test the logic, without pain.

dependency inversionquestion
the answer

Both sides depend on an abstraction.

  • High-level policy should not reach down to low-level detail.
  • Instead, the policy defines an interface it needs; the detail implements it.
  • Now the arrow from the detail points up at the abstraction. That is the inversion.
dependency inversionthe answer
before / after

Inject the dependency. Don't reach for it.

welded to Stripe 

class OrderService {
  // policy reaches down to a concrete detail
  private final StripeGateway gw
      = new StripeGateway();

  void checkout(Order o){
    gw.charge(o.total());
  }
}
// can't swap Stripe; can't test without it
depends on a promise 

interface PaymentGateway { void charge(Money m); }

class OrderService {
  private final PaymentGateway gw;
  OrderService(PaymentGateway gw){   // inject
    this.gw = gw;
  }
  void checkout(Order o){ gw.charge(o.total()); }
}
class StripeGateway implements PaymentGateway { ... }
// tests pass a fake; swap Stripe for PayPal freely

The interface passed in from outside is the seam of this afternoon's capstone. It is also Day 4's composition root, one class that does all the new-ing, and it is the thing Spring's container automates for you.

dependency inversionbefore / after
smell, and rule

The JDK is thirty years old. Would it pass the review you just learned?

No. And it cannot fix any of it, because a public superclass, a public field or a public interface is a promise you can never take back. That is slide 5, at platform scale.

Three releases in a row, so this was not one bad afternoon in 1995. Hands up: which of these have you used this month?

the jdkquestion
inheritance, and abstraction

Exhibit 1: java.util.Stack extends Vector.


public class Stack<E> extends Vector<E> { ... }   // the real declaration, since 1996

Stack<String> s = new Stack<>();
s.push("a"); s.push("b"); s.push("c");
s.add(0, "z");
System.out.println(s.search("z") + " " + s.get(0) + " " + s.pop());
  • A Stack is not a Vector. It has a growable array, and that is a field, not a parent.
  • It inherits Vector's whole positional surface, add(int, e), get(i), remove(i), plus every synchronized lock, so its one invariant, last in first out, is unenforceable.
  • Its own Javadoc sends you elsewhere: a more complete and consistent set of LIFO operations is provided by the Deque interface.

The line prints 4 z c. search counts 1-based from the top; get and add count 0-based from the bottom. One class, two coordinate systems, and they disagree.

Exhibit 2: Properties extends Hashtable<Object,Object>.


Properties p = new Properties();

  • Properties wants String keys and String values. Its parent accepts any Object, so the parent's API walks straight past the child's rule, and the rule has nowhere left to live.
  • getProperty("port") returns null rather than complaining, because the value is an Integer and the method quietly declines to see it.
  • The Javadoc's answer is prose: the use of put and putAll is strongly discouraged. That is a warning where a type should be.

Liskov, and the equals contract

Exhibit 3: Timestamp is a Date that does not equal a Date.


Date d = new Date(0);
Timestamp t = new Timestamp(0);

d.equals(t);
t.equals(d);

// Javadoc: "it is not recommended to view Timestamp values
//           generically as an instance of java.util.Date"
  • Timestamp adds a nanos field, so it overrides equals(Object) to reject anything that is not a Timestamp.
  • equals is now asymmetric, which Object's own contract forbids. You called this one before lunch: true false.
  • The class admits in its documentation that it is not substitutable for its parent. That is the textbook L violation, written down by the authors.

Use instead: java.time.Instant, which carries nanoseconds and never pretends to be a Date.

Effective Java, Item 10
the jdkexhibit 3 · Timestamp
the law behind exhibit 3

You cannot add a value to an instantiable class and keep equals honest.

  • Write equals with instanceof and you break symmetry. That is exactly what Timestamp did.
  • Write it with getClass() and symmetry is safe, but a subclass instance can never equal a parent instance. That breaks Liskov and quietly breaks any collection holding the parent type.
  • There is no third option. So hold the extra value instead of inheriting it: a ColorPoint with a Point field and an asPoint() view.

Set<Date> s = new HashSet<>();
s.add(d); s.add(t);     // size 2
s.clear();
s.add(t); s.add(d);     // size 1, same two objects

Both objects have the same hashCode, because Timestamp never overrides it, so they land in one bucket and the outcome depends entirely on which one is the argument. A broken equals does not throw. It just loses your data.

abstraction

Exhibit 4: Cloneable, an interface with nothing in it.


public interface Cloneable { }      // zero methods. that is the entire file.

class Point implements Cloneable {
    int x = 1;
    Point copy() throws CloneNotSupportedException {
        return (Point) super.clone();
    }
}
// now delete "implements Cloneable" and run it again
  • Implementing an empty interface flips the behaviour of Object.clone() from throwing CloneNotSupportedException to doing a field-by-field copy. Nothing else in Java works like that.
  • The copy it produces skips every constructor, so none of your invariants ever run.
  • A clone of a class with a mutable field is shallow, so the original and the copy share it, which is the record trap from this morning in a different costume.

Use instead: a copy constructor, a static factory, or a record.

abstraction, and interface segregation

Exhibit 5: SwingConstants, an interface used as a namespace.


public interface SwingConstants {
    int CENTER = 0;
    int TOP    = 1;
    int LEFT   = 2;
    // ... and a dozen more
}

public class JLabel extends JComponent implements SwingConstants { ... }
  • Interface fields are implicitly public static final and they are inherited, so JLabel.CENTER, and the same constant on every subclass anyone ever writes, is public API forever.
  • An interface should say what a type can do. This one says what some numbers are.
  • A fat surface that no client asked for: that is I in miniature, and the constant-interface antipattern by name.

Use instead: an enum, or a static import of a final class's constants.

Exhibit 6: a Date you can rewrite from the outside.


final class Period {
    private final Date start;
    Period(Date start) { this.start = start; }
    Date start() { return start; }
}

Period p = new Period(new Date());
p.start().setTime(0);
// so what is p's start now?
  • A private final field on a final class, and a caller just rewrote history through it. Nothing here is a bug in Period.
  • Date has setTime, and a setYear deprecated since 1997. It is a value that is not a value.
  • final protects the reference, never the object it points at. Same sentence as slide 9, different decade.

Use instead: java.time, plus defensive copies whenever you must hand out something mutable.

Effective Java, Items 17 and 50
the jdkexhibit 6 · Date
the same class, two more broken promises

Date is also Comparable. And still mutable.

  • Date implements Comparable<Date>, so a Date works as a TreeMap key. Then somebody calls setTime on it, and the entry is sitting in a position the tree no longer agrees with. You can neither find it nor remove it.
  • Date.toString bakes in the default time zone, so one instant prints differently on two machines, and people compare the strings.
  • getYear() returns the year minus 1900 and getMonth() counts from zero, which is why 2026 turns up as 126 in old log files.

Carry this one line out of the whole run: a mutable key is a bug you cannot see. It is the same rule as the record with a mutable component on slide 9, and you will meet it a third time tomorrow when we do equals and hashCode properly.

encapsulation

Exhibit 7: java.awt.Point with public x and y.


public class Point     { public int x, y; }               // java.awt
public class Dimension { public int width, height; }      // java.awt

Rectangle r = new Rectangle(10, 10);
r.width = -5;        // compiles, ships, and no check exists anywhere
  • That is slide 4's public field, shipped in the platform. The non-negative check has nowhere to go, and never will.
  • The honest cost of Dimension being mutable: getSize() has to allocate a fresh object on every call instead of handing back a shared one, because a shared one could be edited.
  • If you want a real aliasing leak in the same package, java.awt.Polygon exposes its int[] xpoints directly.

Use instead: accessors, or better, record Point(int x, int y).

Liskov, and interface segregation

Exhibit 8: methods the interface promises and the object refuses.


public interface List<E> extends Collection<E> {
    boolean add(E e);        // Javadoc: "optional operation"
    E set(int i, E e);       // Javadoc: "optional operation"
    void clear();            // Javadoc: "optional operation"
}

Arrays.asList("x", "y")             // fixed size, writable in place
List.of("x", "y")                   // no add, no set, nothing
Collections.unmodifiableList(src)   // read-only view of a list that still moves
  • You answered the Arrays.asList version of this before lunch. Here is the cause: the contract itself says "maybe", so the implementer is invited to refuse at run time.
  • Three lists, three different sets of legal operations, and one type. Nothing in the List reference you hold tells you which one you were handed.
  • The fix the JDK could not make in 1998 is separate types: an immutable interface that simply has no add to refuse. Kotlin and Guava both did exactly that.

This is the toy Machine interface from the ISP slide, shipped to nine million developers. A subtype that cannot honour the parent's contract, and an interface fat enough that its implementers must lie.

Effective Java, Items 10 and 20
the jdkexhibit 8 · optional operations
what fixing it actually took

java.time did not patch Date. It replaced it.

  • Every type in java.time is immutable and final. So Instant, LocalDate and Duration cannot be rewritten by a caller, and cannot be subclassed into something that lies.
  • There are no setters at all. Every with method returns a new object, which is why a LocalDate is safe as a map key forever, and a Date never was.
  • Clock is a parameter, not a static call. That is the hidden dependency slide again, and it is the reason java.time is testable in a way Date could not be.

Java 8 could not delete java.util.Date, so both are still in the platform, twelve years later. That is the price of a public boundary: you do not fix it, you outlive it.

Capstone · debrief

Which idea did each test just prove?

  • The bank. The overdraw test that throws: your encapsulation held.
  • A mixed list of transactions through one loop: polymorphism.
  • Transfer added without touching the loop: open for extension.
  • The ledger holding a map instead of extending one: composition.
  • The test that mutates your map after you handed it out: that is encapsulation's second half, and it is the one the JDK failed with Date and Point.
  • The report and the finale. Your own new format just working: DIP and OCP.
  • Every format honouring one one-method contract: ISP and LSP.
  • The service validating while the formatter formats: SRP.
  • The exporter delegating to an injected StatementFormat: that is the seam, and it is the whole reason the finale took ten minutes instead of an afternoon.

what to actually remember

Ten lines, the whole day.

  • Encapsulation: hide state, expose behaviour.
  • Abstraction: program to a simple idea.
  • Inheritance: compose by default; seal the is-a family.
  • Polymorphism: let the object decide.
  • S: one actor, one reason to change.
  • O: extend by adding, not editing.
  • L: a subtype keeps the parent's promises.
  • I: small, role-shaped interfaces.
  • D: depend on abstractions, inject the details.
  • And four traps that look like features: a constructor that calls an override, a record with a mutable component, an interface method that is optional, and a static call you cannot replace.

Plus one meta-rule, courtesy of the JDK: a public boundary is forever, so draw it right the first time.
