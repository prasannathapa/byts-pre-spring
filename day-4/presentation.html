first, the point of all of it

The browser has never heard of Java.

Client and server share one thing: HTTP text on a TCP socket. Everything today is turning those bytes into Java objects and back, and deciding who owns the objects in between.

client-serverthe point
http / the wire

What actually travels down the wire when you press Enter?

You typed a URL. Something left your machine. Write down, in words, what the server received.

httpquestion
the answer, verbatim

Plain text: a request line, headers, a blank line, a body.

request

  • The blank line is the delimiter. Everything above it is metadata, everything below it is the body, and the body is optional. The response mirrors the request exactly, with a status line where the request line was.
  • Every servlet call you meet today is a getter or a setter over one of those lines. That is the whole API, and it is worth holding on to when the method names start piling up.

the trap That charset=UTF-8 is there because somebody typed it. The servlet response default is ISO-8859-1, the JVM's own default has been UTF-8 since JDK 18, and the servlet API never followed. We measure that one before lunch.

the container

Accept, parse, pool, route, wrap, call you.

You could answer a browser yourself with a ServerSocket and a dozen lines. Tomcat is ten megabytes of jar. Here is what those megabytes are doing.

  • The container owns the socket, the threads, the parsing and the objects. You own one method. That is the servlet contract, start to finish.
  • Tomcat's own nesting is worth naming once, because every configuration guide uses it: a Server holds a Service, a Service holds Connectors and one Engine, and under the Engine sit Hosts, Contexts (one webapp each) and Wrappers (one servlet each). The same pipeline sits behind Jetty and Undertow.
containerthe pipeline
the move

Your first servlet is a class with one method.


@WebServlet("/hello")
public class HelloServlet extends HttpServlet {

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse res)
            throws IOException {
        String name = req.getParameter("name");
        res.setContentType("text/plain;charset=UTF-8");
        res.getWriter().print("hello " + name);
    }
}
  • You never construct the request or the response, you never call doGet, and the mapping is a URL pattern rather than a file path. Somebody else owns the control flow. Hold on to that, it comes back at the end of the day.
  • Content type first, then ask for the writer. That order is not a style preference and we will measure why.
  • The import line is the one thing that has changed under everybody's feet. Next slide.

the namespace question

javax.servlet or jakarta.servlet: one API, two names.

Tomcat 9 and older 

import javax.servlet.http.HttpServlet;
import javax.servlet.http.HttpServletRequest;
Tomcat 10 and newer 

import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
  • The two packages are identical class for class and method for method. javax.servlet.http.HttpServlet simply became jakarta.servlet.http.HttpServlet.
  • Code compiled against one will not run against the other, and the failure is a NoClassDefFoundError or a servlet the container never finds: no compiler hint, no warning. Which one you need depends only on the container: Tomcat 9 and the old Java EE servers on javax, Tomcat 10 and later, Jetty 11 and later, and Spring 6 on jakarta.
  • Two packages worth knowing by name: jakarta.servlet, protocol neutral, with Servlet, ServletConfig, ServletContext, Filter and RequestDispatcher; and jakarta.servlet.http, with HttpServlet, the request and response pair, HttpSession and Cookie.
  • The capstone runs Tomcat 11, which implements Jakarta Servlet 6.1, so it is jakarta. You compile against the API jar and never against Tomcat. An interview question phrased with javax is asking about this same API, and your syllabus spells it the old way.
containerjavax vs jakarta
what a servlet actually is

One object, kept by the container, called on every request.

  • Here is the definition the rest of the day rests on. A servlet is a Java class that the container instantiates once, initialises once, and then calls on a worker thread for every matching request. Every rule about fields, about init and about thread safety falls straight out of that sentence.
  • You implement Servlet in an interview answer and you extend HttpServlet in real code. GenericServlet is the rung in between, and it would matter only if you were writing a servlet for a protocol that is not HTTP.
  • The only code you are obliged to write is a doXxx for the methods you answer. Everything else on that chain already has a body.

the response

One response, one buffer, one channel out.


res.setStatus(201);                            // status and headers first
res.setContentType("text/plain;charset=UTF-8");
res.getWriter().print("created");              // characters, encoded for you
// res.getOutputStream()                       // or raw bytes. Never both

res.sendError(404, "no account");              // the container writes the page
res.setStatus(404);                            // your own body survives
  • Ask for the writer or the stream. Whichever you ask for second throws IllegalStateException, because one response has one channel and the container has already decided whether it is encoding characters or copying bytes.
  • Status and headers are decided before you write anything. The body sits in a buffer, eight kilobytes on Tomcat, and once that buffer flushes the status line is on the wire and nothing can take it back. We come back to that at the end of part 2.
  • setStatus keeps the body you wrote. sendError throws it away and substitutes the container's own page, which is right for a browser and wrong for anything expecting JSON.

lifecycle / question

When is your servlet constructed, and how many of them are there?

A thousand people hit /hello this minute. How many HelloServlet objects exist? When was the first one made? Who called the constructor?

One per request

A fresh object each time, like a local.

One per user

Tied to the session somehow.

One per JVM

Built once, kept forever.

One per URL pattern

Three mappings, three objects.

lifecyclequestion
the answer

One instance. Constructed once, init once, service many, destroy once.

  • The unit is the servlet declaration, so one registration mapped to three URL patterns is still one object. The spec requires exactly one instance per declaration per JVM unless the application is marked distributable.
  • Construction is lazy on the first matching request, unless loadOnStartup is zero or more.
  • init runs exactly once, on one thread, before any request. destroy runs once when the context stops, after in-flight requests finish.
Jakarta Servlet 6.1, section 2.2
lifecyclethe timeline
the move

init() is for what you build once; destroy() is for what you must close.


@WebServlet(urlPatterns = "/report", loadOnStartup = 1,
            initParams = @WebInitParam(name = "pattern", value = "dd MMM yyyy"))
public class ReportServlet extends HttpServlet {

    private DateTimeFormatter fmt;                 // built once, then read-only

    @Override public void init() {                 // the no-arg one
        fmt = DateTimeFormatter.ofPattern(getInitParameter("pattern"));
    }

    @Override public void destroy() {
        // close what init opened: pools, executors, files
    }
}
  • Override the no-arg init(). If you override init(ServletConfig config) instead, the first line must be super.init(config), because that is what stores the config. Skip it and getServletConfig() is null, so getInitParameter throws a NullPointerException on the first request, long after a boot you thought had succeeded.
  • A constructor cannot see the ServletConfig. init can. That is the whole reason it exists.
  • Expensive and immutable goes in init. Anything with a close() goes in destroy.
  • loadOnStartup makes a broken init fail at boot rather than on the first unlucky user, and a missing init parameter is the classic reason init blows up.

threads / question

This servlet counts visits. What is wrong with it?


@WebServlet("/hit")
public class HitServlet extends HttpServlet {

    private int hits = 0;

    @Override protected void doGet(HttpServletRequest req, HttpServletResponse res)
            throws IOException {
        hits++;
        res.getWriter().print(hits);
    }
}

It compiles, it runs, the demo works. Two people press refresh at the same instant. Say exactly what can go wrong, and say where hits lives.

threadsquestion
the answer

One instance, many threads: every instance field is shared.

  • hits++ is a read, an add and a write. Two threads can both read 7 and both write 8: a lost update. The container never locks service() for you.
  • Atomicity is only half of it. A plain field written by one request thread has no happens-before edge to a read on another, so the second thread can see a stale value indefinitely, and with a reference field it can see the reference before the constructor's writes have landed.
  • The rule, then. Locals and request attributes are yours. Instance fields and statics are everyone's. A field is safe only if the object is immutable or thread safe.

the trap "It worked for a week" is not evidence. A data race can stay invisible until the JIT hoists a read out of a loop and the field stops being re-read at all.

Effective Java, Items 78 and 83
threadsthe rule
the move

Make it atomic, or make it stateless.

lost updates 

private int hits;

protected void doGet(...) {
    hits++;                    // read, add, write
    res.getWriter().print(hits);
}
atomic 

private final AtomicInteger hits =
        new AtomicInteger();

protected void doGet(...) {
    int n = hits.incrementAndGet();
    res.getWriter().print(n);
}
  • The better answer is usually no state in the servlet at all. Per-user counts go in the session, shared counts go in a thread safe object handed to the constructor, and the servlet stays a thin translator from HTTP to a service call.
  • Safe in a field means one of three things: immutable (DateTimeFormatter, String, a record), thread safe by contract (AtomicInteger, ConcurrentHashMap, a DataSource, HttpClient), or stateless.
  • Synchronizing doGet does fix the count, and quietly makes your server single threaded: one request at a time through that method while the other workers sit idle.
  • Never hold a lock across I/O. A database call inside a synchronized block hands the slowest thing in the system the power to stop every request.

scopes

Request, session, application: three maps with three lifetimes.

A parsed form. A logged in user. A shared price table. Three lifetimes, three homes, and only one of the three you can touch without thinking about threads at all.

scopeobjectlivesvisible tothreads
requestrequest.setAttributeone request, plus forwardsthis request's servlets and filtersone thread

  • getParameter is not a scope. It is the parsed query string and form body, and it is read only. People put it in this table and then wonder why they cannot write to it.
  • Request scope is the free one: one thread owns it, start to finish, so nothing you put there needs a lock. A session value that two tabs can touch should be an immutable snapshot rather than a mutable object you edit in place. Replace the value, do not edit it.

scopesthe three
the move

Same verb, three doors.


String q = req.getParameter("q");                      // read only, already parsed
req.setAttribute("results", results);                  // request scope

HttpSession s = req.getSession();                      // creates one if there is none
s.setAttribute("user", user);                          // session scope
req.changeSessionId();                                 // fresh id, same contents, after a login

getServletContext().setAttribute("prices",             // application scope
        new ConcurrentHashMap<String, Long>());        // thread safe, on purpose

HttpSession existing = req.getSession(false);          // null when there is none
if (existing != null) existing.invalidate();           // logout
  • getSession() creates a session when there is none and sets the cookie, so a getSession() in a filter on /* mints one per crawler hit and each costs memory for thirty minutes. getSession(false) returns null and is the one you want when you are only reading.
  • The two timeout knobs disagree about units. setMaxInactiveInterval(int) is seconds, web.xml <session-timeout> is minutes, and Tomcat's default of thirty minutes reads back as 1800. Setting 30 in code buys you a half minute session and a support ticket.
  • changeSessionId() keeps the attributes and issues a new id. Call it the moment somebody logs in, because an id that was planted before they authenticated is an id somebody else is holding.

dispatch

Forward stays inside; redirect goes back out through the browser.

Your /pay servlet has finished and wants /done to render the result. Only one survives a refresh without charging the card twice.

  • forward keeps one request object inside the container, so request attributes survive and the URL bar still reads /pay. sendRedirect writes a 302 with a Location, the browser asks again from nothing, and the attributes are gone. It also throws IllegalStateException if the response is already committed, because there is nothing left to take back.
  • Post-Redirect-Get falls straight out of that. A POST answered with 200 leaves the browser holding a repeatable POST, so a refresh pays twice. Answer it with 302 or 303 and a Location, and the browser does a GET it can repeat all day.
dispatchforward vs redirect
the third door

include() is forward()'s quieter cousin.


RequestDispatcher d = req.getRequestDispatcher("/header");
d.include(req, res);                                  // runs, and comes back
res.getWriter().print("<h1>Accounts</h1>");
req.getRequestDispatcher("/footer").include(req, res);

// against the form you already know
req.getRequestDispatcher("/done").forward(req, res);  // hands the response over
// nothing after this line may write
  • forward hands the response over completely: the target owns the output and the caller must write nothing afterwards. include runs the target and returns, and both outputs land in the same response in the order they were written.
  • Forward resets an uncommitted buffer. Include never resets anything, which is why include still works on a committed response and forward does not.
  • The included target may not set the status or any header. Its attempts are ignored, because those belong to whoever started the response.
  • req.getRequestDispatcher takes a path relative to the current request; getServletContext().getRequestDispatcher demands a leading slash; getNamedDispatcher("reports") addresses a servlet by its registered name instead of a path.

sessions

A cookie is a ticket; the session is the cloakroom.

HTTP forgets you after every request. Two requests one second apart from the same laptop, and the server has no idea they are related. The cart survives anyway, and that is the whole reason session tracking exists.

  • The cart lives on the server inside an HttpSession. The browser holds nothing but the id. That id is the whole of the security: it must be unguessable, HttpOnly, and on anything real, Secure.
  • The IP address and the connection prove nothing. NAT puts a thousand people behind one address, and connection pools shuffle them anyway.

Writing and reading a cookie by hand.


Cookie c = new Cookie("theme", "dark");

  • getCookies() returning null is the most common NullPointerException on this API. There is no empty array.
  • Name and path together identify a cookie, so setting one at /bank and one at / gives you two cookies with the same name and a bug you will enjoy.

sessions at scale

Sessions, honestly: they are the reason servers stop scaling.

Monday you ran one Tomcat. Tuesday you run two behind a load balancer, and half the requests come back logged out. Nothing in your code changed.

  • The session lives in one JVM's memory, so the other server has never heard of it. Three ways out: sticky sessions (simple, and you lose the session when that node restarts), replication (Tomcat can do it, and it costs network on every write), or no server side session at all, with a signed token in the cookie.
  • Sessions are convenient and they are the first thing that stops you scaling sideways. That is why an API usually carries its identity in a header instead.

URL rewriting: the session id in the path.

Cookies are switched off and your session code has not changed. Where else could the id possibly travel?


// the container appends the id only when it must
String next = res.encodeURL(req.getContextPath() + "/cart");
out.print("<a href='" + next + "'>cart</a>");

// for a redirect target, the sibling call

  • The id rides in a path parameter after a semicolon, not in the query string, so it is not a request parameter and getParameter will never find it.
  • encodeURL is a no-op once the container knows the client accepts cookies, which is why you call it on every link rather than deciding yourself. The first hard coded href drops the user's session.
  • Tomcat 10 and later default to cookies only, so you opt in with <tracking-mode>URL</tracking-mode>. You should not: an id in a URL leaks into logs, Referer headers and pasted links, and anyone holding it is holding the login.

the third mechanism

Hidden form fields, and what they are actually good for.


<form method="post" action="/bank/transfer">
  <input type="hidden" name="from" value="42">
  <input type="hidden" name="csrf" value="9f1c...">
  <input name="amount">
</form>

// server side it is an ordinary parameter, nothing special about it
String from = req.getParameter("from");
  • A hidden field carries state from the page you sent to the POST that comes back, with no cookie and no server side session. That is why the technique predates both.
  • It survives exactly one hop, only through a form submission, never through a plain link. So it cannot replace a session.
  • The user can see it in view-source and edit it before submitting. Anything you trust from a hidden field must be re-checked on the server. "Hidden" means invisible, not secret, and that is the mistake in every price-in-a-hidden-field shopping cart that got looted.
  • The honest modern uses: a CSRF token, a workflow step id in a multi page form, and the id of the row a form is editing.
  • Three tracking mechanisms, compared out loud. Cookies: automatic, survive links and tabs, blocked by privacy settings. URL rewriting: works without cookies, leaks everywhere. Hidden fields: no cookie needed, POSTs only, user editable.

filters

A filter wraps the call: before, chain, after.

Forty servlets. The boss wants method, path, status and milliseconds for every request, and a 401 for anything under /admin without a token. Forty edits, or one?

  • A filter sees the request before the servlet and the response after it, and chains nest: each one wraps the next. Declining to call chain.doFilter short circuits everything, which is how auth returns 401 without your servlet ever running.
  • A filter mapping covers the REQUEST dispatch only, unless you say otherwise. A forward or an include is a fresh dispatch your /* filter never sees. Usually right for logging, a hole for auth. Widen it with dispatcherTypes = {REQUEST, FORWARD} and accept that you will then log twice.
filtersthe chain
the interface underneath

The Filter interface, and what HttpFilter hides.

the interface, in full 

public interface Filter {

    default void init(FilterConfig config)
            throws ServletException {}

    void doFilter(ServletRequest req,
                  ServletResponse res,
                  FilterChain chain)
            throws IOException, ServletException;

    default void destroy() {}
}
a filter written the old way 

public class LoggingFilter implements Filter {

    public void doFilter(ServletRequest r,
            ServletResponse s, FilterChain chain)
            throws IOException, ServletException {
        var req = (HttpServletRequest) r;
        var res = (HttpServletResponse) s;
        chain.doFilter(req, res);
        log(req.getRequestURI()
                + " -> " + res.getStatus());
    }
}
  • Three methods and that is the whole contract: init(FilterConfig) once, doFilter on every request from many threads, destroy once.
  • init and destroy have had default implementations since Servlet 4.0, so a modern raw filter overrides doFilter and nothing else.
  • chain.doFilter(req, res) is the only way the next filter or the servlet ever runs, and what you pass there is what the rest of the chain sees. Hand on an HttpServletRequestWrapper instead of the original and you have changed the request for everything downstream without touching one servlet.
filtersthe raw interface
policy out of the filter

A filter should not know what /admin means.


// the root decides the policy, once
Predicate<HttpServletRequest> needsToken = r -> r.getRequestURI().startsWith("/admin");
addFilter(ctx, "auth", new AuthFilter(needsToken.and(r -> !"OPTIONS".equals(r.getMethod()))));

// AuthFilter has never heard of /admin
private final Predicate<HttpServletRequest> needsToken;

AuthFilter(Predicate<HttpServletRequest> needsToken) { this.needsToken = needsToken; }

protected void doFilter(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
        throws IOException, ServletException {
    if (needsToken.test(req) && req.getHeader("X-Token") == null) { res.setStatus(401); return; }
    chain.doFilter(req, res);
}
  • Predicate<T> is an interface with one abstract method, boolean test(T), and that is the whole of it. That is why a lambda can stand in for it: a lambda is an instance of a one-method interface, written without the ceremony of a class.
  • and(), or() and negate() compose two rules without writing a third class.
  • The filter is now unit testable with a fake request and no container, and the policy sits with the rest of the wiring. That is the point of the last dozen slides of today.
  • You will meet this exact interface again as Spring Security's request matchers. It is the same shape as the removeIf and the stream filter you used on Day 2.

the descriptor

web.xml, and the shape it lives in.


<web-app xmlns="https://jakarta.ee/xml/ns/jakartaee" version="6.0">
  <context-param>
    <param-name>env</param-name><param-value>dev</param-value>
  </context-param>
  <servlet>
    <servlet-name>hello</servlet-name>
    <servlet-class>byts.HelloServlet</servlet-class>
  </servlet>
  <servlet-mapping>
    <servlet-name>hello</servlet-name><url-pattern>/hello</url-pattern>
  </servlet-mapping>
  <filter-mapping>
    <filter-name>log</filter-name><url-pattern>/*</url-pattern>
  </filter-mapping>
</web-app>
  • <servlet> declares the thing; <servlet-mapping> points URLs at it by name. That is why the unit of instantiation is the declaration, and why two mappings naming one servlet still give you one object. The names must match exactly, and a typo is a start-up failure.
  • Filter order in this file is the order the chain runs in, which annotations cannot express. <session-timeout> here is minutes; setMaxInactiveInterval is seconds.
  • The file lives at WEB-INF/web.xml in the WAR, beside classes/ and lib/, and nothing under WEB-INF is ever served to a client.

// both call chain.doFilter, and there is no web.xml in the WAR
@WebFilter("/*") public class AuthFilter    extends HttpFilter { ... }

listeners

ServletContextListener: the container tells you when the app starts.

Something must build the shared price table before the first request. Not in a doGet, that runs per request. Not in one servlet's init, because the others need it too.


@WebListener
public class Startup implements ServletContextListener {

    @Override public void contextInitialized(ServletContextEvent e) {
        e.getServletContext()
         .setAttribute("prices", new ConcurrentHashMap<String, Long>());
    }

    @Override public void contextDestroyed(ServletContextEvent e) {
        // close pools, stop executors, unregister drivers
    }
}
  • contextInitialized runs before any servlet init and before the first request. In the plain servlet world it is the one place where shared objects are built and published.
  • contextDestroyed runs after the last request, in reverse of the start order. Close what you opened: a webapp that leaves a thread running keeps its classloader alive, and memory climbs over a week of deploys.
  • Publishing through a ServletContext attribute means every servlet casts an Object out of a map and trusts that somebody set it. That is the first crack in this design, and it is the reason the afternoon ends where it does.

the other listeners

HttpSessionListener, and the rest of the family.


@WebListener
public class SessionCounter implements HttpSessionListener {

    private static final AtomicInteger LIVE = new AtomicInteger();

    @Override public void sessionCreated(HttpSessionEvent e) {
        e.getSession().setMaxInactiveInterval(15 * 60);   // seconds, not minutes
        LIVE.incrementAndGet();
    }

    @Override public void sessionDestroyed(HttpSessionEvent e) { LIVE.decrementAndGet(); }

    public static int live() { return LIVE.get(); }
}
  • sessionCreated fires on the getSession() that mints one; sessionDestroyed fires on invalidate() or on timeout. That is how you get a live session count that means something, and how you notice that a health check probe is creating a session every thirty seconds.
  • The counter is static and shared across threads, so it is an AtomicInteger for exactly the reason the hit counter was.
  • The rest of the family, named once: ServletRequestListener, HttpSessionAttributeListener, ServletContextAttributeListener, and HttpSessionBindingListener, which an object implements to be told it has just been put into a session or dropped from one.

embedded

Tomcat in ten lines.

No install, no WAR, no deploy step. Pick a port, make a context, register the servlet, start, and stop cleanly. Then java -cp "lib/*:." App and a browser can talk to it.


Tomcat tomcat = new Tomcat();
tomcat.setBaseDir(Files.createTempDirectory("tc").toString());
tomcat.setPort(0);                       // 0 means "any free port"
tomcat.getConnector();                   // this line creates the listener. Do not skip it

Context ctx = tomcat.addContext("", null);
Tomcat.addServlet(ctx, "hello", new HelloServlet(service));   // an INSTANCE
ctx.addServletMappingDecoded("/hello", "hello");

tomcat.start();
int port = tomcat.getConnector().getLocalPort();   // which one did we get
tomcat.stop();
tomcat.destroy();
  • getConnector() must be called or the server starts and nothing listens. It reads like a getter and it is a constructor. That is the trap of this run.
  • setPort(0) asks the operating system for a free port and getLocalPort() reads back which one you got, which is how the capstone tests run in parallel without clashing.
  • You hand addServlet an instance, so the servlet can be constructed with its dependencies. No annotation can do that, and that single fact is what makes this afternoon's composition root possible.

the other registration

Registering a filter in embedded Tomcat: four objects, one name.


FilterDef fd = new FilterDef();
fd.setFilterName("log");
fd.setFilter(new LoggingFilter(log));      // an instance, with its dependencies
ctx.addFilterDef(fd);

FilterMap fm = new FilterMap();
fm.setFilterName("log");                   // must match the def, exactly
fm.addURLPattern("/*");
// fm.setDispatcher("FORWARD");            // opt in, if you want forwards logged too
ctx.addFilterMap(fm);
  • There is no one-line Context.addFilter(name, filter) in embedded Tomcat, so this four object dance is the API and the capstone cannot avoid it.
  • The name in the def and the map must be identical, or Tomcat fails to start with a message that does not point at the typo.
  • You pass a filter instance, which is how a filter receives constructor injected dependencies that an annotation could never give it.
  • The dispatcher call is the code form of dispatcherTypes from the filter slide. Verified against tomcat-embed-core 11.0.26.

json

Right status, right Content-Type, valid JSON, escaped strings.


@Override protected void doGet(HttpServletRequest req, HttpServletResponse res)
        throws IOException {
    long id = idFrom(req.getPathInfo());
    Account a = service.find(id);
    if (a == null) {
        res.setStatus(404);
        res.setContentType("application/json;charset=UTF-8");
        res.getWriter().print(Json.obj("error", "no account " + id));
        return;
    }
    res.setContentType("application/json;charset=UTF-8");   // first, always
    res.getWriter().print(Json.obj("id", a.id(), "owner", a.owner(),
                                   "balance", a.balancePaise()));
}
// Json.str escapes backslash, quote and the control characters. That is the whole trick.
  • No Jackson today, on purpose, so you can see what a mapper does for you and why nobody writes this by hand twice. setStatus keeps your body; sendError throws it away and substitutes the container's HTML page.
  • Set the content type as the first statement, before you ask for the writer. The writer is created with a fixed encoding, so setContentType does nothing once getWriter() has been called, and nothing warns you.
  • The request side is the same shape in reverse: req.setCharacterEncoding("UTF-8") before the first getParameter, because that call parses the body and freezes the decoding.

The servlet prints a rupee sign. What reaches a UTF-8 client?


// JDK 25, where file.encoding has been UTF-8 since JEP 400.
// The client decodes the body as UTF-8.
@Override protected void doGet(HttpServletRequest req, HttpServletResponse res)
        throws IOException {
    res.setContentType("text/plain");
    res.getWriter().print("₹100");     // the rupee sign, then 100
}
  1. A The rupee sign then 100, because the JVM default encoding has been UTF-8 since JDK 18.
  2. B ?100, and the response header says charset=ISO-8859-1.
  3. C Mojibake: the two UTF-8 bytes decoded as two separate characters, the classic broken rendering.
  4. D The rupee sign then 100, because the container adds charset=UTF-8 when you do not name one.

errors

Errors: translate at the edge, or the container decides.

500, and HTML 

protected void doPost(...) {
    service.transfer(from, to, amount);
    // InsufficientFunds escapes,
    // the client gets 500 and a page
    // of Tomcat's HTML
}
409, and JSON 

try {
    service.transfer(from, to, amount);
} catch (InsufficientFunds e) {
    res.setStatus(409);
    res.getWriter().print(
        Json.obj("error", e.getMessage()));
}
  • An exception that escapes service() becomes a 500 carrying the container's HTML page, and a JSON client chokes on markup it never asked for.
  • Translate at the servlet edge: IllegalArgumentException to 400, NoSuchElementException to 404, a broken business rule to 409, anything unexpected to 500 with the stack trace in the log. Never in the response: it names your classes and their versions.
  • A custom error page is declared in the descriptor: <error-page> carrying either an <error-code> or an <exception-type>, plus a <location>. The container forwards to it as an ERROR dispatch, so a filter mapped only on REQUEST never runs for it.
  • res.sendError(404, "no account") triggers all of that machinery; res.setStatus(404) does not. That is why setStatus is what you want when the body is your own JSON.

servlets and jdbc

A servlet talking to a database: who owns the connection.


public final class AccountServlet extends HttpServlet {

    private final AccountService service;      // handed in, never constructed here

    AccountServlet(AccountService service) { this.service = service; }

    @Override protected void doGet(HttpServletRequest req, HttpServletResponse res)
            throws IOException {
        res.setContentType("application/json;charset=UTF-8");
        res.getWriter().print(Json.list(service.all()));
    }
}
  • A Connection is never a servlet field. One instance serves many threads and a JDBC Connection is not thread safe, so you take one from the pool per request and give it back in the same try-with-resources block. That is Day 3, unchanged.
  • The DataSource is built once and handed to the repository, the repository to the service, the service to the servlet. The only class that knows the JDBC URL is the one that boots the application.
  • A leaked connection does not fail, it hangs: ten connections in the pool, two hundred worker threads, and requests waiting in getConnection with an idle database. Keep transactions inside the repository where the commit and the rollback live together, and translate SQLException at the edge like any other exception.

committed

Committed: the point of no return.

  • The response is committed the moment the first byte of the status line and headers goes out. That happens when the buffer fills (Tomcat's default is eight kilobytes), when you call flushBuffer, or when the response ends.
  • After that: setStatus, setHeader, setContentType and addCookie are all specified as ignorable, and Tomcat quietly does nothing.
  • sendRedirect, sendError and forward throw IllegalStateException. include still works, because it never needed to take anything back.
  • isCommitted() tells you which side of the line you are on. resetBuffer() clears the body while you are still on the safe side; reset() clears headers and status as well.
  • The practical rules: decide status and headers before you write anything, keep error translation at the top of the method rather than halfway down the rendering, and remember that a big enough response commits itself without you touching flushBuffer at all.

the answer

The composition root: one place that knows the whole object graph.

  • A composition root is the single place where concrete classes are chosen and wired together. Everywhere else asks for its dependencies in a constructor and never constructs them. That is Day 1's dependency inversion at application scale.
  • Its job is construction and lifecycle, not business logic. It is the only class allowed to import both org.h2 and org.apache.catalina.

the objection

One per process is not the Singleton anti-pattern.

a global variable in a hat 

public final class App {
    private static App INSTANCE;
    public static App get() { return INSTANCE; }
}

// and then, from anywhere at all
AccountService svc = App.get().service();
one instance, no global 

public static void main(String[] args) throws Exception {
    App app = App.start(8080);
    Runtime.getRuntime()
           .addShutdownHook(new Thread(app::stop));
}

AccountServlet(AccountService service) {
    this.service = service;
}
  • Both are one instance per process. The difference is which way the arrows point. With a static accessor, every class depends on App and nothing can be built or tested without it. With constructor injection, App depends on everything and nothing depends on App.
  • A static getInstance hides dependencies inside method bodies where neither the compiler nor the reader can see them, makes a second instance impossible, and leaks state between tests, because a static field outlives them.
  • Spring's ApplicationContext is one per application too, and your beans do not call ctx.getBean(). When you see getBean() in application code, that is this anti-pattern wearing the framework's badge.

App.java: the whole pre-Spring application in twenty lines.


public final class App {
    private final Tomcat tomcat;
    private App(int port) throws Exception {
        JdbcDataSource ds = new JdbcDataSource();
        ds.setURL("jdbc:h2:mem:bank-" + UUID.randomUUID() + ";DB_CLOSE_DELAY=-1");
        Schema.create(ds);
        AccountService service = new AccountService(new JdbcAccountRepository(ds));
        tomcat = new Tomcat();                  // plus setBaseDir, as on the bootstrap slide
        tomcat.setPort(port); tomcat.getConnector();
        Context ctx = tomcat.addContext("", null);
        Tomcat.addServlet(ctx, "accounts", new AccountServlet(service));
        ctx.addServletMappingDecoded("/accounts/*", "accounts");
        addFilter(ctx, "log", new LoggingFilter(new RequestLog()));
    }
    public static App start(int p) throws Exception { App a = new App(p); a.tomcat.start(); return a; }
    public int port()  { return tomcat.getConnector().getLocalPort(); }
    public void stop() throws Exception { tomcat.stop(); tomcat.destroy(); }
}
  • Read the constructor top to bottom and you have the architecture, in dependency order, with no interface left unchosen.
  • The constructor wires and the static factory starts, which is why start() is written as new-then-start rather than reaching for an instance field from a static method.
  • The database name carries a UUID so two Apps in one JVM get two databases, and nothing here is static: the root owns configuration, which is the finale's last test.

the other conflict

H2 in the exercise, MySQL or Oracle in production, and the one line between them.

The real thing: MySQL

Install the server and create the schema. Download mysql-connector-j-9.1.0.jar (Maven coordinates com.mysql:mysql-connector-j) and put it on the classpath with -cp "lib/*:.", exactly as you do here. URL jdbc:mysql://localhost:3306/bank?useSSL=false, with a user and a password. No Class.forName since JDBC 4: the driver jar registers itself through META-INF/services.

Or Oracle

The same code. ojdbc11.jar, URL jdbc:oracle:thin:@//localhost:1521/XEPDB1, a different dialect in the SQL you write by hand, and a different set of error codes to learn.

  • H2 with jdbc:h2:mem:bank buys us one thing: nobody loses the morning to an install. It costs nothing in what you learn, because the JDBC API is identical and only the URL and the jar change.
  • That is the day's dependency inversion, not a convenience. Your servlet, your service and your repository never name a vendor. Only App.java does. Production swaps a DataSource line and your tests keep using H2.
  • The one honest difference to watch is SQL dialect and defaults, which is why people run the same database in tests that they run in production once an application is real.

lazy

Lazy, but safely: Supplier<T> in the root.


// App.java: nothing expensive is built here
Supplier<ReportEngine> reports = memoise(() -> new ReportEngine(ds, templates));
Tomcat.addServlet(ctx, "report", new ReportServlet(reports));
protected void doGet(..) { reports.get().render(res.getWriter()); }   // only now
static <T> Supplier<T> memoise(Supplier<T> once) {   // one build, no race
    return new Supplier<>() {
        private volatile T value;                    // volatile, not plain
        public T get() {
            T v = value;
            if (v == null) synchronized (this) { if ((v = value) == null) value = v = once.get(); }
            return v;
        }
    };
}
  • Supplier<T> is one abstract method, T get(), so a lambda fits. The servlet depends on "something that can give me a ReportEngine" rather than on a ReportEngine, and it still never calls new.
  • The bug this replaces is if (field == null) field = new X() inside doGet: two threads both see null and both build one, and with a plain field a second thread reads a half constructed object.
  • Three arrows in your object graph are one method interfaces: Day 3's RowMapper, the Predicate on the filter slide, and this Supplier. The root chooses the lambda. And this is Spring's @Lazy written out, the same shape as orElseGet.

What is the difference between a framework and a library?

You used H2, java.net.http and Tomcat today. Sort them: which ones did you call, and which one called you?

Then say which of the two the servlet API is, and be ready to defend it.

seguequestion
the answer

A library you call. A framework calls you. That flip is inversion of control.

library

The H2 driver, HttpClient, java.util. You own the control flow. You call in, you get a value back, and nothing happens that you did not ask for.

framework

Tomcat. It owns the accept loop, the worker pool and your servlet's lifecycle. It constructs your servlet and calls init and doGet when it decides. You fill in the blanks.

Don't call us, we'll call you.

the Hollywood principle

  • Inversion of control is a property of who owns the loop and the lifecycle. It is not a product you install.
  • The servlet container is already a framework, and you have been living inside one all day without anybody calling it that.
  • Embedded, you still own main() and choose when to start it. That crack is where the composition root lives. In a WAR the container is also the process, and the crack closes.
  • What it inverts is the request lifecycle only, not the construction of your services. Which is exactly why App.java still has to exist.

  • Every test boots Tomcat on port 0 and talks to it with HttpClient, so nothing else needs to be running and nothing clashes with the person next to you. Logging is pinned to WARNING so the [PASS] and [FAIL] lines stay readable.
  • Expect red. The failures are your to-do list, and they are in the order you should fix them.

recap

Four days, one seam.

HTTP is text

A status line, headers, a blank line, a body. Status and headers are the contract.

The container owns the loop

Sockets, threads, parsing and lifecycle are its. doXxx is yours.

One instance, many threads

Every field is shared. Immutable, thread safe, or no state at all.

Three scopes, three lifetimes

Request, session, application. The session is the expensive one.

Filters wrap, listeners announce

And code beats annotations for anything you need in a known order.

The root builds the application

Once, in one place. Inversion of control is simply who calls whom.
